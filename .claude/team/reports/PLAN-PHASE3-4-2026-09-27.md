### Full JSON backup and restore as new project (capability 1)
`GET /export/backup.json`:
```
{ format: 'e3-tracking-backup', version: 1, exported_at, app: {schema_migration: '0017'},
  client: {key, name, bloomreach_account_id, notes},                       // reference only, never restored
  project: {...every projects column except id, client_id},
  use_case_templates: [...templates referenced by use_cases, full rows],  // re-linked by code on restore
  sources, properties, events, event_sources, event_properties, variants, standard_event_mappings,
  identity_rules, catalogs, catalog_fields, consent_categories, use_cases, requirements, rules,
  property_bundles, property_bundle_items, qa_runs, observations, findings, change_log, comments,
  files: [{path, mime, base64}] }                                          // every file referenced by triggers_json image_path or client_logo_path
```
Every array holds full DAL rows (JSON columns parsed), ids as stored, soft-deleted rows included with `deleted_at` (a backup is a faithful snapshot). Files are embedded as base64 so one file is the whole project (proposed D-45); a missing file on disk becomes a warning in `files_missing[]`, never an error.
`POST /api/projects/restore-backup/preview`: validates `format`/`version`, returns counts per array, the embedded project name and key, `warnings[]` (unknown columns dropped, files missing, templates whose `code` exists with a different definition), and `payload_hash`. `apply`: creates a new project under the given `client_id` (name and key from the body, key must be free), then in one transaction inserts every row with **every id remapped** to a fresh UUID: the restorer builds `idMap` from all `id` columns first, then deep-walks every row (keys and values of parsed JSON columns included) replacing any string equal to an old id, which covers `conditions_json[].property_id`, `field_map_json` values, `expression_json` refs, `context_values_json` keys, `event_property` composite ids in `change_log.entity_id` and `parent_entity_id`, and the `finding.fingerprint` (ids inside the pipe-separated string are rewritten by the same map, so D-42 acknowledgements survive). `use_case_templates` are matched by `code`: an existing template with an equal definition is reused, a different definition is a warning and the use case keeps `template_id` of the existing one, a missing template is created. Files are written through `FileStore.put` under the new project id and the stored paths rewritten. One `change_log` row `action: restore` with the source key and counts is appended; then `runComparison` recomputes. Never merges into an existing project. Test: fixture project (scenarios 2, 3, 4, 8, one trigger screenshot) -> backup -> restore -> per-table counts equal, `tracking-document.json` of both equal after masking ids, timestamps and `generated_at`, screenshot served from the new project path.

## History, share and comment design

### ChangeLog write points (DAL level, one transaction with the mutation)
`src/backend/dal/change-log.dal.ts`: `recordChange(db, {projectId, entityType, entityId, entityLabel, parentEntityId?, action, before, after})` computes `diff_json` with `diffValue` per field over the union of keys (excluded: `created_at`, `updated_at`; `deleted_at` is expressed by the action), skips empty updates, reads actor/source/batch from `getActor()`. Every mutation function listed in the verified-facts scan calls it inside its own `db.transaction` (functions that were not transactional become so): `createX` after the insert (after = row read back), `updateX` (before = row read before the UPDATE), `deleteX` (before = row; soft delete counts as `delete`), `replaceEventProperties`/`replaceRequirements`/`reorder*` write one row per link that changed (create/update/delete each with its own diff), `upsertStandardEventMapping` picks create or update, `createRulesFromTemplate` one row per rule, `updateProject` for settings changes (entity_type `project`, label = name). Imports: apply services run inside `runWithActor({source: 'import:<format>', batch_id})`; nothing else changes because the planners already call the DAL. MCP: today's write tools touch QA evidence only (not logged); the wrapper is still installed so future definition writes carry the agent name.

### Share token (capability 13, D-14, phase 5 ready)
One token per project (project-wide, CONTEXT.md capability 13). `POST /share` generates `randomBytes(32).toString('base64url')` (43 chars), stores it in plaintext in `projects.share_token` with `share_access` and `share_created_at`; a second `POST` rotates (old link dies); `DELETE` nulls all three. Plaintext, not hashed, because the Settings page must re-display the link (proposed D-48; hashing plus one-time display is the phase 5 option if the app is hosted). No expiry, no login, no per-entity tokens. `requireShare` compares with `crypto.timingSafeEqual` on equal-length buffers. The public URL is `<origin>/tracking-plan/shared/<token>` (frontend route), which calls `/api/shared/<token>/...`; both are relative so the same build works on localhost and, in phase 5, behind a host. Phase 5 adds rate limiting and optional hashing at the middleware; nothing else changes.

### Shared documentation view (D-10 reuse of the renderer)
`src/pages/SharedProject.tsx` mounted in `App.tsx` for paths matching `/shared/:token` (before `ProtectedRoute`; no `AuthProvider` requirement, `fetch` without `fetchWithAuth`). Loads `GET /api/shared/:token` then `GET /api/shared/:token/tracking-document.json` and renders: project header (name, client, logo via the shared files route), table of contents, one `EventCardView` per custom event (the presentational component extracted from `src/pages/EventCard.tsx` in T-4-03, taking `EventCard` data plus a `fileUrl(path)` resolver and a `commentsSlot`), then sdk/platform events collapsed, use cases (narrative plus ordered requirements), identity rules with codegen, consent categories, catalogs, standard event mappings, findings summary; download links for the tracking document JSON and the documentation HTML from the shared routes. Read-only: no edit controls render (the presentational component has no mutation props). Plain layout (D-07).

### Comments (capability 13)

## Proposed decisions (for the supervisor to record in DECISIONS.md)
- **D-44 ChangeLog is written at DAL level inside the mutation transaction with the actor from an AsyncLocalStorage context.** Context: capability 12; PLAN-2026-09-24 asked for a DAL mutation helper; routes, imports and MCP all call the DAL. Decision: `change_log` table (0015) with entity type, id, label, parent id, action create/update/delete/restore, actor, source (`ui | mcp | import:<format> | restore | system`), batch id, field diff; `recordChange` called by every definition-mutating DAL function inside its transaction; actor/source/batch from `src/backend/context/actor.ts`, set by Express middleware, the MCP wrapper and import services. Evidence tables (qa runs, observations, findings), clients and the global template library are not logged. Consequences: no history can be missed by a new route; imports appear as one batch; the plan-2024 `import_apply` action is replaced by `source`; restore writes one row plus the carried log.
- **D-45 Backup is one self-contained JSON with embedded files; restore only creates a new project and remaps every id.** Context: capability 1; the brief asks for ids remapped and files included or referenced. Decision: format `e3-tracking-backup` v1, every table as full rows including soft-deleted ones, files base64-embedded (missing files are warnings), referenced templates embedded; restore is preview/apply (D-22), never merges, remaps every id by a deep walk over keys and values of every JSON column and rewrites finding fingerprints so D-42 acknowledgements survive, re-links templates by code, writes files under the new project, then recomputes findings. Consequences: a backup is portable between machines; restore of a large project is a single request under a 100 MB limit; cross-project copy (D-27) stays a separate feature (D-54).
- **D-46 CSV export contract.** Context: capability 9, scenario 6. Decision: headers declared once in `src/domain/csv.ts` (list in this plan), ids next to names, JSON columns as compact JSON strings, booleans `true`/`false`, UTF-8 with BOM and CRLF through papaparse, soft-deleted rows excluded, one route per entity plus a listing route; no CSV import ever (D-01). Consequences: files join on ids in a spreadsheet; the header lists are the tested contract and any change is a plan-level edit.
- **D-47 Use case library format and instantiation rules.** Context: D-06, capability 11. Decision: `e3-use-case-library` v1 with `default_requirements` in the shape the DAL already resolves; import is preview/apply merged by `code` (D-22 pattern, global scope, not logged); export emits the same shape; instantiate copies the template code as the use case code with a numeric suffix on conflict, keeps the exact-variant-condition resolution and `gap` fallback, copies notes and generates the narrative. A three-template sample lives in `samples/`. Consequences: the user's 90 templates load through the same path; template deletion is refused while instantiated.
- **D-48 Share token design.** Context: capability 13, phase 5 readiness, D-14. Decision: one token per project, 32 random bytes base64url, stored in plaintext so Settings can re-show the link, access `read | comment`, rotate on regenerate, revoke by nulling, no expiry, no login, timing-safe comparison, public routes under `/api/shared/:token/*` (document JSON, HTML, files, comments) with 404 for unknown or revoked tokens; frontend route `/tracking-plan/shared/<token>`. Hashing with one-time display and real rate limiting are phase 5 hosting concerns added at the middleware. Consequences: a leaked link is revoked by rotating; no per-entity or per-user sharing; the shared view is usable on localhost for QA. Phase 5 option (user, 2026-09-27): an optional passphrase per share link, stored hashed, checked once per browser session via cookie, added together with token hashing and rate limiting when the app is hosted; not part of phase 4.
- **D-49 Comment model.** Context: capability 13. Decision: `comments` table (0017) on `event | property | use_case | requirement` with free-text author, body, `via_share`, internal-only resolve and delete, no edit; comments are excluded from the tracking document and MCP and included in backup and CSV; `replaceRequirements` keeps requirement ids for unchanged targets so comments do not orphan. Consequences: the smallest model that lets a client annotate the document; threads, mentions and notifications are out of scope.
- **D-50 The shared view is a React page fed by the tracking document from the share route and reuses the event card renderer.** Context: D-10 asked to reuse the documentation rendering; D-34 made `EventCard` the shared unit. Decision: `EventCardView` is extracted from the internal card page as a presentational component; the shared page renders the tracking document (custom events first) with it, plus use cases, identity, consents, catalogs, mappings and download links; `EventCard` gains `triggers[]` (additive, no version bump) so screenshots render through the shared file route. Consequences: one renderer for the internal card, shared view, HTML and MCP; the HTML export keeps data-URI images.
- **D-51 Dead-code sweep list and legacy documents.** Context: D-02, D-18; the old plan's candidates are already gone. Decision: delete the five unimported files, four empty directories, ten Supabase/journey-era documents under `docs/` and `.cursor/rules/project-context.mdc`; reduce `src/types/schema.ts` to what codegen still imports; keep `store.tsx` (UI state), `ApiAuthConfig.tsx` and the served user manual (content refresh is a docs task). Consequences: `docs/` holds only DOMAIN, QA-LOCAL, TRACKING-DOCUMENT, MCP, EXPORTS, SHARING; the sweep runs alone after every other phase 3 task merges.
- **D-52 QA evidence is editable and deletable; variant deletion refuses while mapped.** Context: T-2-08 QA and T-2-05 review follow-ups. Decision: `PATCH/DELETE /observations/:id` (hash recomputed, duplicate 409), `DELETE /qa-runs/:id` (findings keep their rows with null run and observation refs, 0008), each followed by a recompute; `deleteVariant` returns 409 `MAPPING_IN_USE` unless `force=true`, which clears the mapping's variant first. Consequences: no silent conversion of a filtered mapping into an unfiltered one; evidence corrections are visible through recompute rather than history.
- **D-53 Migration numbers for phases 3 and 4** (extends D-39). Decision: 0014 T-2-09 (`findings.resolved_by`, already on its branch), 0015 T-3-01 `change_log`, 0016 T-4-01 `projects.share_created_at`, 0017 T-4-02 `comments`; no other task adds a migration without asking the supervisor for the next number.
- **D-54 Cross-project copy with provenance and the drift compare view are deferred past phase 4.** Context: D-27 placed them in phase 3; the D-43 phase 3 brief lists history, backup, CSV, library import and the sweep, and CONTEXT.md capability 1 names them. Decision: not built in phases 3 or 4; backup and restore-as-new-project covers cloning a whole brand project; the `origin_project_id`/`origin_entity_id` columns are added when the copy feature is scheduled (user to confirm priority at the phase 4 report). Consequences: capability 1 stays "partial" in the exit report; nothing in phases 3 and 4 blocks adding the columns later.
