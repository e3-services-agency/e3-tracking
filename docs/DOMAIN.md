# Domain model

Plain-words companion to the `domain-model` skill and `.claude/team/CONTEXT.md` section 3. Numbers in parentheses are `.claude/team/DECISIONS.md` records.

## Entity model

- **Client** — a Bloomreach account (a mother company). Holds one or more Projects (D-27).
- **Project** — one Bloomreach project or brand. The unit of work: everything below is scoped to a project, and a project exports a full JSON backup.
- **Event** — a Bloomreach event type (`purchase`, `view_item`, ...). `class` is `custom | sdk | platform` (D-29, D-36): custom events are defined and implemented by the client and are what the migration is about; sdk events (`session_start`, `page_visit`, ...) and platform events (`campaign`, `consent`, `survey`, ...) are produced by Bloomreach itself and are informational only — the comparison engine never validates them and certification is `not_applicable` for them. `src/domain/bloomreach.ts`'s `SDK_EVENT_TYPES`/`PLATFORM_EVENT_TYPES` classify known system names on import; a Data Manager name outside both lists defaults to `custom` (D-40 Q7). `implementation_method` (D-63, migration `0025`) says how the event reaches Bloomreach: `client_web` (a dataLayer push read by a GTM custom template or the Web SDK), `server_api` (the Tracking API; the default for `purchase`, `purchase_item`, refund-like and `consent` events) or `sdk_auto` (emitted by the SDK or the platform, the default for `sdk`/`platform` class events). It decides which implementation snippets the event card shows. `dl_event_name` records the site's dataLayer event that carries the Bloomreach event (per event, with the variant's discriminator documented on the event; there is no per-variant column). Validation always runs on the Bloomreach event payload, never on the dataLayer.
- **Property** — a field, either event-scoped or customer-scoped (`scope: event|customer`). Customer properties are Property rows with `scope: customer`, not a separate table (D-24). A property carries its own enum values in `allowed_values_json`, one list shared by every event that uses it (D-16). An `array`-typed property may declare an `item_schema` (`item_schema_json`: `[{field, data_type, data_formats[], required}]`, D-30) validated per list item. `kind` (D-63) says where a value comes from in the recommended dataLayer object `bloomreach`: `event` (`bloomreach.properties.x`), `item` (an attribute of the one item interacted with, `bloomreach.item.x`), `state_list` (computed from the whole collection `bloomreach.items` by its `derivation_json` rule: `{source: 'items', id_field, form: 'ids' | 'id_quantity', quantity_field?}` gives `product_ids` / `product_list`-style lists, `{source: 'items', sum: 'price*quantity'}` gives a total) or `context` (a project-wide attribute, tracked as an SDK default property). Property bundles (`property_bundles`) group properties, for example the item shape; the event editor's "Add bundle" links every property of a bundle in one step and the tracking document shows a property's bundle name.
- **EventProperty** — the link between an Event and a Property: required, role (`normal | discriminator | context`), status, source, payload key, priority. Per-event overrides (renamed field, example values) live here, not on Property (D-16).
- **Rule** (D-30, D-31) — a declarative check attached to an Event, optionally scoped to one of its Variants. `kind` is `arithmetic | membership | bound | cross_event`; `expression_json` holds typed JSON operands (`property | list_field | constant | product | aggregate` refs), never a string DSL — `src/domain/rules/types.ts` is the grammar, `src/domain/rules/operators.ts` the aggregate/comparator/bound-check registries, `src/domain/rules/evaluate.ts` the pure evaluator. `tolerance_mode` is `none | money | absolute | percent` (`money` resolves from the project's `money_tolerance_percent`/`money_tolerance_floor`); `report_kind` (`rule_violation | bound_violation | rounding_drift`) defaults from `kind` and is `rounding_drift` only for a money `cross_event` rule, preserving the phase 1 purchase-vs-purchase_item finding. `severity` defaults to `error`, `warning` allowed (D-40 Q4). Rules and item-schema checks run inside comparison `definition_vs_observations` (`src/domain/rules/runRules.ts`), not as a separate comparison. `src/domain/rules/templates.ts` ships seed templates (`purchase_items_total`, cart_update product-list checks, purchase-refund bound checks) a project can apply.
- **Variant** — an Event plus conditions on one or two discriminator properties, for example `cart_update[action=add]`. This is the only thing that creates a variant; location-like context properties never do (D-03). Conditions are normalized (deduped, sorted, a one-value `in` collapsed to `equals`) so equivalent condition sets share one identity. Bloomreach's own data-mapping filter format is exactly this shape, so export is one to one.
- **Context property** — an enum property (page location: product page, listing, minicart, checkout, ...) that never creates a variant. QA reports a variant x context coverage grid (observed vs unobserved cells) instead of authoring every combination.
- **StandardEventMapping** — maps a Bloomreach standard event key (seed list in `src/domain/bloomreach.ts`, extensible per project, D-26) to an Event or Variant plus a field map.
- **Identifier** — one of the project's fixed identifiers: a hard id, a soft id or the cookie (D-69, migration 0032). `identifiers` holds `name` (unique per project, case-insensitive), `type` (`hard` | `soft`), `description`, `is_cookie`, `sort_order`; it is edited on the Settings page in two lists like the Bloomreach project settings screen. Renaming one cascades to every identity rule and every `events.identifiers_json` entry that uses it; deleting one is 409 `IDENTIFIER_IN_USE` while a rule or an event references it. The type and cookie flag live here only: a rule's `identity_type` is derived from its identifier.
- **IdentityRule** — an identification *act* of one Identifier (`identifier_id`, `ON DELETE SET NULL`; several rules may act on one identifier, e.g. `cart_id` set on checkout by GTM and also by the backend; the Identification flow paragraph aggregates them per identifier). Compatibility: POST/PATCH with `identifier_name` (+ `identity_type` for a new name) finds or creates the identifier. Describes when hard/soft customer IDs are set and when customer properties/events may be sent. A rule is set either by its trigger event or, when `trigger_event_id` is null, by a **standalone call** (`sdk_call` + `trigger_text` + source, e.g. GTM sending `identify({cookie, cart_id})` on the checkout page, D-67 amendment 1). `Event.identifiers_json` (migration 0030) lists the identifier names an event sends in `customer_ids`; empty means the derived default (client_web/sdk_auto: the cookie and every `identify` rule; server_api: rules whose source is one of the event's sources). `src/domain/identity/identifiers.ts` derives it, builds each rule's `set_by` (`event` | `standalone_call` | `unknown`), `binds` (the identifiers a standalone call sets together: the cookie for a web source, the source's other identifiers for a server one) and `carried_by`, and writes the deterministic **Identification flow** paragraph (it names the profile merge when events carry only the standalone-set identifier). The paragraph appears on the Identity rules page, the event card, the tracking document (`identification_flow`), the HTML export and the shared view; comparison 3 raises `identifier_missing` (warning, Identity family) when an observation that records `customer_ids` lacks one the event carries (D-67). A **Source** also has a palette colour `sources.color` (`source-1`..`source-8`, auto-assigned by system, D-68).
- **Catalog** — a Bloomreach catalog definition (fields, mapping role). Since D-61 a project can hold one per market and language; see "Catalogs per market, catalog checks and sources" below.
- **Source** — where an event is collected from: a system (`shopify`, `custom_backend`, ...) and a collection method (`web_sdk_gtm_datalayer`, `tracking_api`, ...), D-62.
- **ConsentCategory** — a client-specific consent category mapped from a standard consent key (seed list, extensible per project, D-26), matching the Bloomreach mapping's `consents: {newsletter: "brand_consent"}` shape.
- **UseCaseTemplate** — a global library entry (D-06), not project-scoped: code, name, type, description, `default_requirements` (D-55: `target_kind`, `standard_event`/`event_name`, `property_name`, `condition`, `level`, `note`), plus tags and flags (D-57, see "Use case library" below). Adding one to a project creates a project's `UseCase`.
- **UseCase** — a client instance of a template, or a client-specific one. Carries an ordered list of Requirements, which doubles as the flow sequence, and a generated, editable narrative (no diagram, D-10).
- **Requirement** — one use case's need for a target, `level: required|optional`, in `sort_order`. Target kinds: `customer_property`, `event`, `variant`, `event_property`, `variant_property`, plus `catalog_attribute` (a main-catalog field, resolved by name, D-57) and `consent` (a consent category, resolved by name, D-57).
- **QaRun** — one batch of observations: `kind` is `export_paste` (an applied `customer-events-export.json` paste, through the Import page or the MCP `submit_observations_batch` tool), `agent_session` (one or more `submit_observation` MCP calls reusing the same run within a process, D-33), or `manual`. `DELETE /qa-runs/:id` cascades its observations and recomputes findings (D-52).
- **Observation** — one observed event instance (raw type, raw properties, resolved `event_id`/`variant_id`, page context if from an agent session). `PATCH /observations/:id` edits the evidence in place (`raw_hash` recomputed, 409 on a duplicate within the run) and `DELETE /observations/:id` removes one; both recompute findings immediately (D-52).
- **Finding** — one typed QA result, deduplicated by fingerprint (comparison, kind, event, variant, property, detail) and upserted on every recompute (D-21). `status` is `open | resolved`; `resolved_by = 'user'` marks a manual acknowledgement via the Findings page (D-42, see below) as opposed to `null` for an automatic resolve by the recompute engine.
- **ChangeLog** — one row per definition-mutating write (D-44, capability 12), written at DAL level inside the same transaction as the mutation: `entity_type`/`entity_id`/`entity_label` (the label survives the entity's own deletion), `parent_entity_id` (groups a child row — an event property, a variant, a requirement — under its parent's history panel), `action` (`create | update | delete | restore`), `actor` (the local user's display name, an MCP agent's `agent_name`, or `system`), `source` (`ui | mcp | import:<format> | restore | system`), `batch_id` (shared by every row one import apply or restore produces, so the History page groups them), and `diff_json` (`[{field, before, after}]` over top-level fields, JSON columns compared by value). The actor/source/batch come from an `AsyncLocalStorage` context (`src/backend/context/actor.ts`), set once per HTTP request, once per MCP tool call, and around an import apply or restore — no route or DAL call threads it explicitly. Not logged: QA evidence (`qa_runs`/`observations`/`findings`, which have their own lifecycle), `clients`, and the global `use_case_templates` library. `GET /api/projects/:id/history` lists rows newest-first with filters (`entity_type`, `entity_id`, `parent_entity_id`, `action`, `actor`, `source`, `batch_id`, `since`) and keyset pagination (`before`/`before_id` or a single `"<changed_at>|<id>"` cursor, `next_cursor` in the response); the MCP `get_history` tool mirrors it read-only.

## The four comparisons (D-11, D-21, D-28, phase 2)

A fifth, `catalogs` (D-61, T-4-11B), checks the catalogs themselves and needs no observations; it is described under "Catalogs per market, catalog checks and sources".

All four run together on every `POST /comparison/run` (and the MCP `run_comparison` tool), orchestrated by `src/backend/services/comparison.service.ts`; each engine's findings are upserted by fingerprint and stale fingerprints resolve per-comparison (a comparison never resolves another comparison's findings).

1. **Definition vs mapping** (`definition_vs_mapping`, `src/domain/comparison/definitionVsMapping.ts`) — the project's Event/Property/Variant/Catalog definitions against the last applied `data-mapping.json`/`expiration-settings.json` (a `MappingSnapshot`, D-22). Findings: `unmapped_standard_event`, `unmapped_property`, `rename_mismatch`, `unmapped_catalog` — all warning. These also surface as import preview warnings at paste time (D-04); this comparison recomputes them against the *current* definitions on every recompute, not just at import time.
2. **Mapping vs observations** (`mapping_vs_observations`, `src/domain/comparison/mappingVsObservations.ts`) — the applied mapping/expiration settings against what Bloomreach actually received (customer events export paste or agent observations). Findings: `rename_mismatch`, `unknown_variant`, `missing_required` — all warning, except `missing_required` (error). `missing_event` is not duplicated here — comparison 3 owns it for every mapped-or-not custom event.
3. **Definition vs observations** (`definition_vs_observations`, `src/domain/comparison/definitionVsObservations.ts`) — the phase 1 comparison, the most detailed of the four. Every observation in every non-archived QA run is re-resolved against the *current* definitions on each recompute (a stale `event_id`/`variant_id` never sticks). Also runs the Rules and item-schema evaluators (`src/domain/rules/runRules.ts`) as part of this same comparison id, not a separate one.
4. **Definition vs Data Manager** (`data_manager`, `src/domain/comparison/definitionVsDataManager.ts`, D-28/D-37) — the project's custom-event definitions against the last applied `data-manager-events.json`/`data-manager-customers.json` snapshot. Findings: `type_mismatch` (error when the Data Manager type is known, warning otherwise), `unmapped_property` (warning), `missing_event` (warning), `unexpected_property` (info). Custom events only, matching comparison 3's own class exclusion.

## Finding kinds and severities (D-21, D-30)

Twenty-seven kinds total: the twelve from the `qa-roundtrip` skill (`missing_required`, `type_mismatch`, `format_violation`, `enum_violation`, `unknown_variant`, `shape_inconsistent`, `rename_mismatch`, `unmapped_standard_event`, `unmapped_property`, `expiration_mismatch`, `rounding_drift`, `unexpected_property`), three added by D-21 (`missing_event`, `unexpected_event`, `unmapped_catalog`), three added by D-30's rules layer (`rule_violation`, `item_schema_violation`, `bound_violation`, all error), and `state_list_mismatch` (D-63, T-4-17, error: the lists of a state list group disagree in length or id type, or the interacted id is missing after `add` / still present after `remove` with quantity 0), and `naming_violation` (D-65, T-4-22, warning, comparison 1: a custom event, event property or customer property name does not follow the project's naming convention; see "Naming convention" below). D-61 (T-4-11B) adds seven catalog kinds under the fifth comparison id `catalogs`: `catalog_searchable_limit` (warning at 40, error above), `catalog_searchable_changed`, `catalog_lookup_key`, `catalog_lookup_property`, `catalog_type_mismatch` (all error), `catalog_schema_drift` and `catalog_link_missing` (warning); see "Catalogs per market, catalog checks and sources" below. Families: Schema (limit, lookup key, lookup property, type mismatch), Consistency (searchable changed, schema drift), Coverage (link missing). T-5-32 adds four Data Manager declaration kinds under comparison 4 (family Data Manager), reading only the `source`, `used` and `private` flags so they work on masked data: `dm_auto_declared` (warning: an event or property with `source: data`, which Bloomreach wrote itself when unrecognised data arrived, that the plan does not declare or declares with a different type; the declaration is descriptive, not designed), `dm_unused` (info: `used: false` in Data Manager while the plan has the event as implemented or links the property), `pii_not_declared` (error: private in Data Manager, PII unset in the plan) and `pii_not_private` (warning: PII in the plan, not private in Data Manager). Fingerprints are per event and property, so manual resolve and acknowledgement behave as for every other kind. A Data Manager export written by the app itself marks app-born entries `used: false`, so importing it back produces `dm_unused` for those.

### Finding families and labels (T-4-21)

`src/domain/findingsCatalog.ts` gives every comparison id and every finding kind a human label, a one-sentence explanation and a "what to do next" sentence, and groups the kinds into six families used by the findings summary: **Schema** (`missing_required`, `type_mismatch`, `unexpected_property`, `unknown_variant`, `item_schema_violation`, `naming_violation`), **Values** (`enum_violation`, `format_violation`), **Arithmetic** (`rounding_drift`, `bound_violation`, `rule_violation`), **Consistency** (`state_list_mismatch`, `shape_inconsistent`, `rename_mismatch`, `expiration_mismatch`), **Coverage** (`missing_event`, `unexpected_event`, `unmapped_property`, `unmapped_standard_event`, `unmapped_catalog`) and **Data Manager** (every finding of the `data_manager` comparison, whatever its kind). A test fails when an enum value has no entry. The shared view, the HTML export, the Findings page and the event cards show the label with the explanation as a tooltip; the raw ids stay in the JSON and CSV exports. The same sentences are in the Help glossary.

Severity table (D-21, D-25 Q4/Q5, D-30, D-37):
- **error**: `missing_required`, `type_mismatch` (definition-vs-observations and known-type Data Manager mismatches), `enum_violation`, `unknown_variant` (definition side), `shape_inconsistent`, `missing_event` in agent sessions, `rule_violation`, `item_schema_violation`, `bound_violation`, `state_list_mismatch` (bound rules may opt into `warning` per rule, D-40 Q4).
- **warning**: `format_violation`, `rounding_drift` (unless a rule's own `severity` overrides it), `rename_mismatch`, `unmapped_property`, `unmapped_standard_event`, `unmapped_catalog`, `naming_violation`, `expiration_mismatch` (mapping side), `missing_event` in export pastes and in the Data Manager comparison, `unknown_variant` (mapping side), `type_mismatch` (unrecognized Data Manager type).
- **info**: `unexpected_property`, `unexpected_event`, `expiration_mismatch` (observation side).

Known Bloomreach system event types (`consent`, `survey`, `campaign`, `support_ticket`, `managed_endpoint`, `session_start`, `session_end`, `page_visit`, `web_exit`, `notification_state`, `first_session`, `banner`, `experiment`, and similar, seed list in `src/domain/bloomreach.ts`) are excluded from `unexpected_event` (D-25 Q5).

`rounding_drift` is anchored on the `purchase`/`purchase_item` standard-event mapping, now a seeded `cross_event` Rule template (`purchase_items_total`, D-31) rather than hard-coded: sum of item price times quantity per `purchase_id` versus the purchase total, tolerance 0.01 in the purchase currency by default (D-21, D-25 Q12, project-configurable via `money_tolerance_percent`/`money_tolerance_floor`). Monetary properties carry data format `money`.

Expiration suppresses `missing_event` when the newest observation in scope is older than the event's effective expiration window (D-21).

## Bloomreach Data Manager formats (D-28, D-35, D-37, D-41)

Two more import/export formats join `data-mapping.json`/`expiration-settings.json` (D-04): `data-manager-customers.json` (customer properties, grouped) and `data-manager-events.json` (event definitions, each with its own property list and group). Both use paste-in preview and apply through the shared diff mechanism, and export reproduces the input shape byte-for-byte on an untouched project.

- Bloomreach types (`string, number, boolean, date, datetime, list, long text, url`) map to the app's `data_type` + `data_formats` both ways (`src/domain/bloomreach/dataManagerTypes.ts`, D-37): `long text` → `string` + format `long_text`; `url` → `string` + format `uri`; `date` → `timestamp` + format `iso8601_date`; `datetime` → `timestamp`; `list` → `array`; the rest map one to one; an app `object` property (or any other unmapped type) exports as `string` with a warning.
- Event/property-level flags the app has no concept of (`source`, `used`, `deleting`, `forbidden`, `real_time_analytics`, `locked_for_contact_migration`, `are_all_used`, `default_private`, `default_forbidden`) live in a `bloomreach_meta_json` column per entity (`properties`, `events`, `event_properties`) and are written back untouched so untouched projects round-trip exactly (D-28, D-35).
- A property's type from a Data Manager row with `source: user` (a person defined it in Bloomreach) is proposed as a definition update; a type from `source: data` (inferred from incoming data) is never proposed — it is stored as evidence (`dm_type`) and reported by comparison 4 instead (D-35). The same property name with conflicting types across events creates the Property once (first `user` occurrence, else first) with one warning (D-41).
- The last applied `data-manager-customers.json`/`data-manager-events.json` payloads are stored verbatim on the project (`data_manager_customers_json`/`data_manager_events_json`) as the comparison 4 evidence snapshot and the export passthrough source for deselected sdk/platform events (D-35).
- Unknown Data Manager event names default to Event `class: custom` unless they match the known sdk/platform lists (D-29, D-40 Q7).

## Certification (D-05, D-21, D-42)

An event is **certified** when:
1. `class === 'custom'` (`applicable: true` — sdk/platform events are never certified, reason `not_applicable`, D-29/D-36), and
2. Status is not `ignored`, and
3. Zero open **error** findings exist for the event across all four comparisons, and zero **acknowledged** error findings (see below, D-42), and
4. At least one observation of the event exists in a non-archived QA run (D-25 Q10) — a mapped but never-observed event cannot certify.

Certification is computed on read, never stored (`src/domain/certification.ts#computeCertification`); it changes automatically when definitions, mapping, Data Manager evidence, or observations change. `reasons[]` lists what blocks it, in a fixed order: `not_applicable` (exclusive), `status_ignored`, `` `open_errors: n` ``, `` `acknowledged_errors: n` ``, `no_observations`; empty exactly when `certified` is `true`.

**Manual resolve is an acknowledgement, not a fix (D-42).** The Findings page's Resolve toggle (`PATCH .../findings/:id {status: 'resolved'}`) sets `resolved_by = 'user'` and takes the finding out of the open list and the event card's `findings[]`, but it still counts toward `acknowledged_errors: n` for as long as the same fingerprint keeps reproducing on recompute — a person cannot flip an event to certified by dismissing a finding without fixing the underlying problem. Once a recompute stops reproducing that fingerprint, the marker clears automatically and the finding is fully resolved; an explicit reopen (`PATCH .../findings/:id {status: 'open'}`) clears the marker immediately. A later recurrence reopens the finding as an ordinary open finding.

The certified data product card that surfaces this (name, owner, status, grain, identity, variants, contexts, freshness, quality, agent instructions, rules, codegen) is the `EventCard` (`src/domain/document/trackingDocument.ts`, built by `src/backend/services/document.service.ts#buildEventCard`), shared by the in-app event card page, the HTML documentation export, the machine-readable tracking document, and the MCP `get_event_card` tool. See `docs/TRACKING-DOCUMENT.md` for the full field list.

## Use case library and templates (D-06, D-47, D-55, D-57)

`UseCaseTemplate` rows live in a global table (`use_case_templates`, no `project_id`), maintained through `GET /api/use-case-templates` (list/one), `GET /export.json`, `POST /import/preview`, `POST /import/apply` (the `e3-use-case-library` format, preview-then-apply by payload hash like every Bloomreach import, D-22, merged by `code`: `create`/`update`/`unchanged`), and `DELETE /:id` (409 `TEMPLATE_IN_USE` while any non-deleted use case still references it). A template's `default_requirements` name a **Bloomreach standard event** (`standard_event`) and standard property names rather than the client's own event names, so the same library works across clients (D-55); `event_name` is used instead only for a custom event outside the standard catalog. Adding a template to a project (`POST /use-cases/from-template/:id`, or its `/preview` sibling for a dry run) resolves each requirement in order: (1) the project's own `StandardEventMapping` for that standard event, translating property names through its `field_map`; (2) an exact name match against the project's events/properties; (3) anything still unresolved is returned as a candidate list, and the apply body's `mappings: [{index, event_id, variant_id?, property_id?}]` answers those rows, each saved as a new `StandardEventMapping` before the requirements are created (so later templates, and comparison 1, resolve automatically too). A target that stays unresolved (skipped, or genuinely absent from the project) becomes a requirement with `status: gap`. The MCP tools `list_use_case_templates`/`instantiate_use_case_template` (the tool name is the code identifier) mirror the same routes and resolution order, `dry_run` mapping the preview.

Templates also carry optional **tags** (`channels`, `goals`, `tiers`, `kpis`, `industries`, suggested vocabularies in `src/domain/enums.ts` mirroring Bloomreach's own Use Case Center) and **flags** (`new`, `popular`) — D-57, unknown tag values import as a warning, never an error. The Use case templates page filters by the five facets and shows a per-template prerequisites card (events, customer properties, catalog attributes, consents, each with a resolved/gap/mixed status against the current project). A project's own optional `industry` field (`projects.industry`) is the templates page's default facet filter.

## Backup and restore (D-45, capability 1)

`GET /api/projects/:id/export/backup.json` produces one self-contained JSON file per project: every table as full rows (soft-deleted rows included — a backup is a faithful snapshot, not a filtered export), JSON columns parsed, every referenced file (trigger screenshots, the project logo) embedded as base64, and referenced `use_case_templates` embedded in full; the project's `share_token`/`share_access` export as `null` so a restored copy never silently reuses a live public link. `POST /api/projects/restore-backup/preview` and `/apply` (unscoped — the target project does not exist yet) follow the same preview-then-apply, payload-hash pattern as a Bloomreach import (D-22): apply always creates a **new** project (never merges), remapping every row's id to a fresh UUID and deep-walking every row (including inside parsed JSON columns) to rewrite any string that equals an old id — this is what keeps a `Finding`'s fingerprint, a `Variant`'s conditions, and a `change_log` row's `entity_id`/`parent_entity_id` internally consistent after restore. `use_case_templates` are the one array re-linked rather than recreated: an existing template with the same `code` and an equal definition is reused, a different definition is reused with a warning, a missing one is created. One `change_log` row (`action: restore`) records the restore, then `runComparison` recomputes findings on the new project.

## Naming convention (D-65, T-4-22, phase 4)

`projects.naming_convention` (migration `0028`, default `snake_case`, CHECK on `snake_case` | `kebab_case` | `camel_case`, enum `NAMING_CONVENTIONS`) is chosen in Project settings. It applies to **custom events, their properties and customer properties**. The pure `src/domain/naming.ts` holds the rule: `matchesConvention(name, convention)` (a single lower-case word follows all three; snake_case `order_total`, kebab_case `order-total`, camel_case `orderTotal`) and `isNamingExempt(entity)`. **Exempt**: `sdk` and `platform` class events, SDK default properties (`os`, `browser`, `device`, `location`), the reserved system customer properties (`email`, `phone`, `first_name`, `last_name`, `country`, `language`, `timezone`) and standard event keys (always snake_case, as Bloomreach requires). Exemption follows `classifyProperty`, so a manual category override to `customer` or `event` lifts it.

Enforcement never blocks a save. The event and property name inputs show an inline warning when a non-exempt name does not conform. Comparison 1 emits a `naming_violation` finding (warning, Schema family) per nonconforming name, so names that arrive through an import surface as findings; a property linked to several events is reported once. The data-mapping import preview does not run the naming check; `runComparison` is the only producer of `naming_violation`. The editor warning is a hint for any event-scope property, while findings cover properties linked to custom events and customer properties (an unlinked event property gets no finding). The shared page shows "Naming convention: snake_case (system items exempt)" under the Events and Properties headers.

## Cross-references, copy buttons and badges (T-4-22)

A small copy button next to every entity name (events, properties and their definitions, use cases, consent categories, standard event keys, catalogs and catalog fields) copies the exact name, on the shared page and on the internal list pages and editors. Property rows and event card property tables carry a category badge (System customer and SDK default in the Bloomreach accent, Customer and Event neutral). References link to their target through one pure helper, `src/features/shared/references.ts` (`resolveReference`/`referenceHref`): on the shared page "Used in" events, property keys inside an event card, a catalog's "looked up by" properties and event or property use case requirement targets jump to the `#event-<slug>` or `#property-<slug>` anchor (a property row opens when targeted); internally the same references open the event card or the Properties editor.

## Property definitions (D-58, T-4-00, phase 4)

A `Property` keeps one shared identity (name, payload key stays on the link, data type, PII, source); `property_definitions` (migration `0021`) holds one or more **named meanings** per property — `name`, `description`, `allowed_values_json`, `formats_json` (the property's own data-format list, not a single value — a property can carry several at once, e.g. `email` and `uri` both ticked, and every one is checked per event), `example_values_json`. `EventProperty.definition_id` (nullable, `ON DELETE SET NULL`) is which definition a given event's link uses, validated to belong to the same property; every consumer that reads allowed values/formats/description/examples (comparison 3's per-event enum/format checks, comparison 4, the event card, the tracking document's `properties[].definitions[]` and per-property `definitions_json` on event links, codegen, the HTML documentation export, the Data Manager events export) reads them through the link's definition, falling back to the property's own fields only when a link carries none (defensive, every link is resolved to a real definition by the DAL).

**Examples of an enum come from its allowed values** (T-5-11): when `allowed_values_json` is non-empty, `exampleValuesFor` shows the stored examples that are allowed values first, then allowed values until there are two; a stored example outside the set is ignored everywhere (event card, tracking document, exports, shared view) and the editor and API write responses warn (`warnings: ["example X is not an allowed value"]`, never a 400). Without allowed values the stored examples are used as is.

Every property gets one `general` definition seeded from its own fields at creation time. Until phase 5 drops the now-redundant property columns, `general` and the property's own `description`/`allowed_values_json`/`data_formats_json`/`example_values_json` stay mirrored **both ways** inside one transaction: editing the property syncs `general`; editing `general` directly (from the Properties page's definitions section) syncs the property back. A property with a single definition therefore behaves exactly as it did before this table existed. `data_type` stays at the property level everywhere — no definition can change it; the Data Manager import's cross-event type-difference check still only warns, never proposes an update (D-41 unchanged).

`property.dal.ts#deleteProperty` soft-deletes every one of the property's definitions in the same transaction, so a definition never outlives its property as a *live* row (CSV export joins on the property's own `deleted_at` and so excludes a definition whose property is soft-deleted; the full JSON backup, true to D-46's "faithful snapshot, not a filtered export", still carries those rows with `deleted_at` set, same as every other soft-deleted row in a backup).

`property-definition.dal.ts`: `listDefinitions`/`createDefinition`/`updateDefinition` (409 on a duplicate name)/`deleteDefinition` (409 while any event link still uses it, or when it is the property's last remaining definition — a property always has at least one meaning)/`reorderDefinitions`, `getDefaultDefinitionId` (the `general` definition, or the first by sort order if `general` was renamed away), `listAllDefinitionsById`/`listDefinitionsByPropertyIds` (batched, project-wide reads used by `document.service.ts`'s `EventCardBuildContext` and `comparison.service.ts`'s `buildDefinitionSnapshot` so building a card or running comparison never issues one definition query per link). Routes under `/api/projects/:id/properties/:id/definitions` (`GET`/`POST`, `PATCH`/`DELETE .../:definitionId`, `PUT .../order`); the Properties page expands a property row into its definitions (add/edit/remove, using events); the event editor's property row shows a definition picker only when the property carries more than one.

The migration backfill (and, on import, the Data Manager events planner's `definition_create`/`definition_update` preview items) names an override definition after the first event it was linked to; when that name would collide with the property's own `general` definition (an event literally named `general`, or a definition already named that), it is renamed `"<event> (event)"`, with a numeric `-2`/`-3` suffix on any further collision.

## Property categories and system customer properties (D-64, T-4-20, phase 4)

Every property has a **category**, derived at read time by the pure `classifyProperty` (`src/domain/propertyCategory.ts`, the one definition module for `PROPERTY_CATEGORIES`):

| Category | Rule |
| --- | --- |
| `system_customer` | customer scope and the name is one of the reserved list below |
| `customer` | any other customer-scope property |
| `sdk_default` | event scope and the name is one of `os`, `browser`, `device`, `location` (`SDK_DEFAULT_PROPERTIES`); such a property is kind `context` unless a kind was set explicitly |
| `event` | everything else; on the shared view, the Markdown copy and the HTML export it is sub-grouped by the D-63 kind (event, item, state list, context) |

`properties.category_override` (migration `0027`, nullable, CHECK on the four values) is a manual override that wins over the derivation; there is no backfill. It is **not** `properties.category`, which has existed since `0001` and holds the Bloomreach Data Manager group name (free text, round-tripped by the Data Manager customers import and export). The Properties page has a Category column, a category filter and a "Property category" select ("Automatic" or one of the four). A definition inherits its property's category and is nested under it.

Reserved system customer properties and the format hint each gets when it is created or imported with no formats (stored in `data_formats`, so comparison 3 checks observed values against it like any other format):

| Property | Recommended format | Format id | Checked |
| --- | --- | --- | --- |
| `email` | a valid email address | `email` | yes |
| `phone` | E.164 (`+421900123456`) | `e164_phone` | yes |
| `first_name`, `last_name` | Title Case | `title_case` | no, recommendation only: shown, never a finding |
| `country` | ISO 3166-1 alpha-2, upper case (`SK`) | `country_code` | yes |
| `language` | ISO 639-1, lower case; a BCP 47 region is allowed (`en`, `pt-BR`) | `language_tag` | yes |
| `timezone` | IANA time zone name (`Europe/Bratislava`) | `iana_timezone` | yes |

`language_tag`, `iana_timezone` and `title_case` were added to the data formats. `language_tag` accepts a lower-case alpha-2 language with an optional upper-case alpha-2 region only (`en`, `pt-BR`; house rule, not full BCP 47), and `title_case` is displayed as "Title Case (recommended)". In the UI a property whose name is an SDK default (`os`, `browser`, `device`, `location`) implies kind `context` when its kind is still the default. Comparison 3 reads observed *event* payloads (there is no observation channel for customer attribute values), so the checks run on an event property that carries one of these formats, and on the `item_schema` fields that name them. Sources for the reserved names: `.claude/team/samples/br-docs/data-and-assets/data-structure/customers/customers.md` (`first_name`, `last_name`, `email`) and `.claude/team/samples/br-docs/reference/bloomreach-identity-reference.md` (`email`, `phone` E.164 with plus, `language`, `first_name`, `last_name`); the SDK defaults come from `.../data-structure/custom-events.md`. The docs do not list `country` or `timezone` as reserved; they are here because D-64 names them.

## Catalogs per market, catalog checks and sources (D-61, D-62, T-4-11B, phase 4)

**Catalogs per market.** A catalog has a `kind` (`product` | `variant` | `other`, derived from the mapping role or `catalog_type` when not chosen), a `market`, a `language` and a `version` (`v1` | `v2`). Catalogs of one kind (normally one per market) must share one schema. The two Bloomreach mapping roles stay single per project (`main` product catalog, `variant` catalog), normally the default market; the data-mapping export is unchanged and still byte-equivalent on an untouched project. "Mark live" (Catalogs editor, `POST /catalogs/:id/live`) sets `live_at` and stores the searchable field names at that moment (`searchable_snapshot_json`), the baseline for the v1 rule below; "Take off live" clears both.

**The `catalogs` comparison** (`src/domain/comparison/catalogChecks.ts`, no observations needed, run by `runComparison` with the others). Per catalog: `catalog_searchable_limit` (warning at 40 searchable fields, error above), `catalog_searchable_changed` (error: a live v1 catalog whose searchable set differs from its go-live snapshot), `catalog_lookup_key` (error: no lookup key field, or more than one), `catalog_lookup_property` (error, D-61 amendment: the field flagged as lookup key is the `item_id` column, which Jinja cannot read because it reads only properties, so every product or variant catalog with a lookup key also needs a regular non-key field with the same value, named like the key's `client_field_name` or else `product_id` / `variant_id`; it fires whatever `bloomreach_column` says, and when the key field itself has that name the advice is to rename it to item_id and add the regular field). Across catalogs of the same kind (`other` is not compared): `catalog_schema_drift` (warning, one finding per kind and field: a field missing in some markets, or a type or searchable flag that differs). Alignment: `catalog_type_mismatch` (error: a property linked to a catalog field has a different data type; catalog and property type names are compared by family, an unknown type name is never flagged) and `catalog_link_missing` (warning: an event property named `product_id`, `item_id` or `variant_id` that is not linked to the lookup key of a catalog of the matching kind). The Properties editor has the catalog field picker that sets the link. Observed-value matching against catalog items is deferred until a catalog item export fixture exists.

**Catalog attribute requirements** resolve per kind: the reference field is the main catalog's, and the field is then looked up in every catalog of the main catalog's kind (`product_id` and `item_id` are the same field under two names). Present everywhere: satisfied. Missing in some market: still resolved to the main catalog's field, but created with `status: gap` and a note `Field "x" is missing in: CZ, ...`; the add-to-project dialog shows the per-market result and the prerequisites card reads "mixed".

**Sources.** A source has a `system` (`shopify` | `magento` | `salesforce_commerce_cloud` | `custom_backend` | `mobile_app` | `crm` | `erp` | `other`, default `other`) and an optional `method` (`web_sdk_gtm_datalayer` | `web_sdk_direct` | `tracking_api` | `bloomreach_integration` | `file_import`), shown as "Shopify via GTM data layer". A linked source's method defaults the event's implementation method (`tracking_api` -> `server_api`, the web methods -> `client_web`) but only while the event still has the default `client_web` and the request names no method of its own: an explicit choice is never overridden. The project's **default source** (Settings) is linked to every new event that names no source of its own. The codegen block opens on the tab matching the source's method (GTM data layer -> dataLayer, direct Web SDK -> Web SDK, Tracking API -> Tracking API) when that tab exists for the event's implementation method. Event cards, the tracking document (`sources[]`, `events[].sources`, `project.default_source`), the shared view and the Markdown copy carry system and method.

## Share link and the public documentation view (D-48, D-50, phase 4)

A project has at most one share link (`share_token`, `share_access: read | comment`,
`share_created_at`). It needs no login (`/tracking-plan/shared/<token>`) and serves a **public
projection** of the tracking document and HTML export — internal-only fields
(`agent_instructions`, `owners`, `identity_note`, `bloomreach_project_url`, every `internal_*`
field) are stripped, `not_suitable_for` stays. Access `comment` additionally shows a comment form.
Every route error is the identical 404 `SHARE_NOT_FOUND`, and responses never cache. A sandbox
project (see below) refuses a share link unless the request explicitly forces it. Full detail in
`docs/SHARING.md`.

## Comments (D-49, phase 4)

A `Comment` attaches to an `event`, `property`, `use_case`, or `requirement` — free-text author and
body, no edit, only resolve (internal-only) and delete. **A comment thread is one shared thread**
(D-49 amendment): whether posted internally or through a `comment`-access share link, every comment
on an anchor is visible on both sides. `via_share` records where a given comment was *posted*, not
who can *see* it. Comments never appear in the tracking document, the HTML export, or any MCP tool
output; they do appear in the full JSON backup and the `comments` CSV entity.

## Sandbox projects (D-60, phase 4)

The app bundles a fully-loaded sample project (`.claude/team/samples/sandbox-project-backup.json`,
rebuilt by `scripts/build-sandbox-backup.mjs`). "Create a sandbox" (Clients page) restores it as a
brand-new project under a chosen or auto-created "Sandboxes" client, flagged `is_sandbox` in
`projects.settings_json`. A sandbox is badged in the switcher and Clients list, refuses a share link
unless the request explicitly forces it, and is meant for exploration and onboarding rather than
real client data — a backup of a sandbox restores as a sandbox.

## Glossary (T-4-09)

`src/domain/glossary.ts`'s `GLOSSARY` is the one place every app term (certified, acknowledged,
definition, variant, discriminator, context, gap, requirement level, batch, activation, sandbox) is
defined in plain words. The Help page renders the full list; a `GlossaryTerm` tooltip attaches the
same text to the first occurrence of a term in a page header or table column. Add a new term there,
not inline in a component.
