# Audit 2026-09-24

## Summary (10 lines max)
e3-tracking is a working React 19 + Express app backed entirely by Supabase (Postgres/Auth/Storage); there is no local persistence path today (D-09 is unmet). Its domain model covers Events, Properties, EventProperty (presence only), Catalogs, Sources, and an ad-hoc "EventVariant" (named override bag), but has no Discriminator/Context role, no Variant-as-conditions, no IdentityRule, no ConsentCategory, no UseCaseTemplate/UseCase/Requirement, no Observation, and no Finding — the whole three-way-comparison/certification engine in CONTEXT.md does not exist. There is no Bloomreach JSON import/export (customer events export, data mapping, expiration settings) anywhere in the code. The "QA overlay" (`src/lib/qaOverlayInjection.ts`) is not a live frontend-event capture mechanism; it injects manually-entered QA proofs/screenshots into a static exported HTML brief. No Google Sheets or Apps Script coupling exists in code — the Sheet is only a documented predecessor, not a dependency. A legacy, disconnected Zustand store (`src/store.tsx`) still powers `Settings.tsx`'s CSV import/export and audit config against an always-empty in-memory model, separate from the real Supabase-backed Events/Properties pages — this is dead/misleading code. No test runner is configured; `npm run lint` is `tsc --noEmit` only. Of the 13 required capabilities in CONTEXT.md section 4, roughly 2 are Present, 4 are Partial, 7 are Missing.

## Data model as implemented
All types live in `src/types/schema.ts` (Phase-1 relational types, used by API/DAL) and the older `src/types.ts` (pre-Supabase client shape, still used by `src/store.tsx`/`Settings.tsx`). Two parallel models coexist (see Risks).

- **Workspace** ("Project" equivalent): `WorkspaceRow` `src/types/schema.ts:183-191`, settings in `WorkspaceSettingsRow` `src/types/schema.ts:193-205`. No client-facing JSON "full project backup" export exists (see Import/export section).
- **Event**: `EventRow` `src/types/schema.ts:301-326`. Fields: name, description, purpose, event_type (track/page/identify — not custom/system per CONTEXT.md 3.2), owner_team_id, categories, tags, triggers (`EventTriggerEntry[]`), codegen name overrides. No `expiration` field on events anywhere in schema.ts or the migrations (`supabase/migrations/*.sql` grep for `expiration` found nothing).
- **Property**: `PropertyRow` `src/types/schema.ts:234-263`. Fields: context (event/user/system_property), name, description, category, pii, data_type, data_formats, value_schema_json, example_values_json, name_mappings_json, catalog mapping. No `allowed values` / enum list field on `PropertyRow` itself (no `allowed_values` or `enum` column in schema.ts or migrations).
- **EventProperty**: `EventPropertyRow` `src/types/schema.ts:381-387` — only `event_id, property_id, presence, created_at, updated_at`. **No `role` field** (`normal | discriminator | context` from the domain-model skill is absent). No `required` flag on this row either (required-ness is computed elsewhere via `EventPropertyDefinitionRow.required`, `src/types/schema.ts:436-449`, which is a separate per-event override table, not the base link).
- **"Variant"**: implemented as `EventVariantRow` (`src/types/schema.ts:407-417`, migration `supabase/migrations/20260329180000_event_variants_v1.sql:1-16`) — a named "implementation scenario" under a base event with a free-form `overrides_json: EventVariantOverridesV1` (`src/types/schema.ts:392-405`) keyed by arbitrary property overrides (presence/required/excluded/description/example_values/enum_values). The migration comment itself says "not Avo-style global variants" (`supabase/migrations/20260329180000_event_variants_v1.sql:1`).

## Persistence and Sheet dependency
- All durable reads/writes go through `getSupabaseOrThrow()` (`src/backend/db/supabase.ts:47-51`), which throws `ConfigError` (mapped to HTTP 503, `src/backend/app.ts:72-79`) if `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` are unset. There is no fallback local store (file, sqlite, in-memory persisted).
- Frontend auth also requires Supabase directly: `src/lib/supabase.ts:8-18` throws if `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` are missing; `AuthContext.tsx:22-45` drives login/session off Supabase Auth exclusively — there is no local/no-auth dev mode.
- `better-sqlite3` is an unused, dead dependency (see Stack section) — no local SQLite persistence exists despite the dependency's presence.
- **What the app needs from remote services today, concretely**: (1) a live Supabase Postgres project for every DAL call (`src/backend/dal/*.dal.ts`, all import `getSupabaseOrThrow`), (2) Supabase Auth for login/session (`AuthContext.tsx`), (3) Supabase Storage for uploaded images/screenshots (journey step images, QA proof images — referenced via public storage URLs, e.g. `src/backend/services/export.service.ts:379-386`). Google Fonts and a highlight.js CDN are also fetched at runtime in exported HTML (`src/lib/qaOverlayInjection.ts:112-113`, `src/backend/services/export.service.ts:1217-1220`) but that's cosmetic, not app-critical.
- **Can it run and persist fully on localhost today?** No. `npm run dev` will start Vite, but every data operation (login, any Events/Properties/Catalogs/Sources/Journeys CRUD, QA runs) requires a reachable Supabase project over the network; nothing runs against a local database or file. This directly fails D-09 ("no task may depend on a remote service to be verified").
- **What it would take to be local-first**: replace the Supabase Postgres dependency with a local persistence engine (the already-declared but unused `better-sqlite3`, or a JSON-file store) behind the same DAL interface, and replace Supabase Auth with a local/no-auth dev mode or a stub session, and replace Supabase Storage with local filesystem writes for uploaded images. This is a substantial rewrite of `src/backend/db/`, all 12 files in `src/backend/dal/`, `src/lib/supabase.ts`, and `AuthContext.tsx` — not a config change.
- **Google Sheets / Apps Script coupling**: none found in code. A repo-wide case-insensitive grep for `sheet|apps script|spreadsheet|google sheet` matched only: `.claude/` docs, `CLAUDE.md`, `README.md`(implicitly via docs), `.cursor/rules/project-context.mdc`, `public/docs/user-manual/getting-started.md`, `docs/PRODUCT_REQUIREMENTS.md`, and UI components/pages whose "Sheet" hits are the unrelated `src/components/ui/Sheet.tsx` slide-over panel component and its usages (`PropertyEditorSheet.tsx`, `EventEditorSheet.tsx`, `Sources.tsx`, `Properties.tsx`, `AddPropertyModal.tsx`, `EventAttachPropertyPicker.tsx`, `Modal.tsx`, `Sidebar.tsx`, `Events.tsx`, `CatalogFormModal.tsx`, `JourneyDescriptionEditor.tsx`, `generateHandoff.ts` — all UI "Sheet" panels, not Google Sheets). **Deleting Google Sheets support is a no-op in this codebase because no such integration exists**; the only real "legacy" artifact is `.claude/team/samples/legacy-workbook-structure.md`, a reference doc.

## QA overlay
`src/lib/qaOverlayInjection.ts` (746 lines) does **not** capture live frontend events from a client website. It is a pure-function HTML/CSS/JS-string builder that:
1. Builds a `<style>` block for QA chips/run cards (`buildQaOverlayStyleString`, lines 23-107).
2. Builds a per-run `<script>` block (`buildQaOverlayScriptString`, lines 127-704) that, **at HTML-view time in the browser**, renders a `QARun` object (tester name, environment, per-node `QAVerification` with manually typed notes, manually pasted `proofText` JSON payloads, and uploaded proof images/screenshots) into the exported implementation-brief HTML, matching each verification to its journey step/trigger section by node id.
3. Splices that style+script into the exported HTML via `injectQaOverlayIntoExportHtml` (lines 738-745), called from both the browser export path (`SharedJourneyView.tsx`) and the backend export path (`export.service.ts`), per the file's own header comment (lines 1-14).

The actual "comparison" performed is client/tester-driven **payload validation**, not capture: `src/backend/lib/eventPayloadEnumValidation.ts` and `assertEnumValuesForQaRunPayloads` (called from `src/backend/dal/qa.dal.ts:153`) check a tester-pasted JSON payload's keys/enum values against `event_property_definitions`, and store pass/fail plus issue strings on the `QAProof` (`validation_status`, `validation_issues`, `src/types.ts:112-113`). QA run data itself is stored as opaque JSON in `qa_run_payloads.expected_json` per node id, with sentinel node ids for run metadata/canvas snapshot (`RUN_META_NODE_ID`, `RUN_NODES_NODE_ID`, `RUN_EDGES_NODE_ID`, `src/backend/dal/qa.dal.ts:33-35`) — there is no `actual_json` usage beyond a hardcoded `'{}'` placeholder (`src/backend/dal/qa.dal.ts:219,239` etc.), confirming no expected-vs-actual machine comparison exists.

There is no code anywhere (`postMessage`, `window.addEventListener` on a target site, injected tracking pixel/bookmarklet, browser extension) that captures events as they fire on the client's live website. CONTEXT.md capability 10 ("QA overlay capture of frontend events feeding observations") and the domain-model's `Observation` entity (source: `export` | `frontend`) are both **Missing**, not partially present — despite the filename similarity, this is a different feature (manual QA evidence overlay for a static doc export) that happens to share the name "QA overlay."

## Risks
- **Remote hard-dependency contradicts D-09.** Every DAL call throws without a live Supabase project (`src/backend/db/supabase.ts:18-42`); there is no way to demo or test the app fully offline today. Highest-priority fix before any further feature work, per the decision record.
- **Dead/misleading legacy data path.** `src/store.tsx` is a from-scratch, never-hydrated Zustand store still wired into `Settings.tsx` (CSV import/export, audit config, handoff generation) and referenced by `Layout.tsx:6,106,113-114,116,195` for workspace-key state. A user clicking "Export CSV" today gets an empty or stale file with no error, which is a silent-failure/trust risk independent of the CONTEXT.md rebuild. Should be resolved (delete or rewire) regardless of refactor-vs-rebuild choice.
- **No tests at all.** Any refactor (or rebuild) has zero regression safety net; `npm run lint` only type-checks.
- **Two incompatible "Variant" concepts.** The existing `EventVariantRow`/`overrides_json` model and UI (`src/features/events/editor/EventVariantsSection.tsx`, `CreateVariantModal.tsx`) will collide semantically with the CONTEXT.md D-03 Variant (event + discriminator conditions). Any migration must decide whether to repurpose, rename, or fully replace this entity — naming collision risk for agents and users alike.
- **No secrets/PII scan performed** beyond noting `PropertyRow.pii: boolean` exists as a flag (`src/types/schema.ts:241`) — its enforcement (e.g., redaction on export) was not verified as in scope for this audit.
- **CORS reflects any origin by default** (`getCorsOrigin()` returns `true` when `CORS_ORIGIN` unset, `src/backend/app.ts:27-31`) — acceptable for local/dev, a production hardening item, not a local-first blocker.
- **Google Sheets/Apps Script deletion is a non-event.** Confirmed no code depends on it; D-01/D-02's "retire Sheets" consequence requires no code removal in this repo, only the human workflow change and, if desired, deletion of `.claude/team/samples/legacy-workbook-structure.md`'s status as "reference only" (already documented as such).

## Recommendation: refactor core or rebuild core, with reasons

**Recommendation: rebuild the core domain model and Bloomreach import/export/comparison layer; keep and adapt the surrounding application shell.**

Reasons to rebuild the core (Event/Property/Variant/Requirements/Observation/Finding + Bloomreach import-export-diff + three-way comparison):
- None of capabilities 3, 4, 5, 6, 8, 10, 11 exist in any partial form — there is no existing code to refactor toward the target shape; a Variant-as-conditions model, discriminator/context roles, IdentityRule, ConsentCategory, UseCaseTemplate/UseCase/Requirement, Observation, and Finding are all new tables, types, and UI from zero.
- The one existing lookalike (`EventVariantRow`) is built on an incompatible premise (free-form named scenario, not discriminator conditions) and would cost more to bend into shape than to replace, given it's config-shaped JSON (`overrides_json`) rather than structured conditions.
- The QA/observation side needs an entirely different capture model (typed `Observation` + `Finding` vs. today's free-text tester-entered proof strings) — there's no algorithm or data flow to reuse, only the export-rendering plumbing.

Reasons to refactor (not rebuild) the rest, keeping this recommendation from being a full rewrite:
- Events, Properties, Catalogs, Sources already have solid, workspace-scoped, RLS-protected CRUD with a mature editor UI (`src/features/events/`, `src/features/properties/`, `src/features/catalogs/`) — capability 2's table-editing backbone for these four entities is genuinely reusable.
- The codegen/export pipeline (`export.service.ts`, `codegen.service.ts`) already produces per-event/per-trigger documentation with real payload examples and is the strongest existing asset toward capability 7 (per-event documentation card) — extend it rather than replace it.
- The enum-from-one-definition pattern (`PROPERTY_DATA_TYPES`, `CATALOG_TYPES`, etc. in `src/types/schema.ts`) is exactly the pattern CONTEXT.md wants generalized to all enums (discriminator allowed-values, consent categories, etc.) — reuse the convention.
- The DAL/route/RLS architecture (Express + per-entity DAL files + workspace middleware) is sound and workspace-isolated; swapping the storage engine underneath it for local-first (per D-09) is a scoped, bounded piece of work rather than a reason to discard the architecture.

Main risks of "rebuild the core":
- Scope creep: it's tempting to also rebuild the (working, actively-used) Journeys/canvas feature, which is out of CONTEXT.md's required-capability list entirely; must be explicitly fenced off as "keep as-is" to avoid re-litigating a feature nobody asked to change.
- Migration of the existing `EventVariantRow` data (if any client workspaces already have variants defined) needs an explicit decision — CONTEXT.md D-02 says no legacy compatibility is required, which simplifies this, but the decision should be recorded explicitly so agents don't attempt to preserve it.
- Two "Variant" names existing simultaneously during a transition period is a concrete risk for confusing future agents/tasks; the plan should rename or remove the old concept in the same phase the new one is introduced, not leave both live.

Main risks of "refactor the core" (rejected path, recorded for completeness):
- Bending `EventVariantRow.overrides_json` into a conditions-list shape while keeping the same table/route contract would produce a worse data model than starting clean, since the free-form JSON was never designed to enforce "at most two discriminators" or "enum-only conditions" (domain-model skill rule 3), inviting silent invalid states.
- Retrofitting `Finding`/`Observation` onto the existing `QAProof.validation_issues: string[]` free-text shape would require parsing/reverse-engineering prose that was never structured, for no benefit over just adding the new typed tables.
