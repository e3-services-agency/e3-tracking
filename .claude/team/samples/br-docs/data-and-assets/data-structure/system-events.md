# System events

System events are events available to all Bloomreach customers by default. Unlike [custom events](https://documentation.bloomreach.com/engagement/docs/custom-events), system events are consistent across all projects—no custom integration needed. This article explains each system event and its attributes.

## Session events

| Event           | description                                                                                                                                                                                         |
| :-------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `session_start` | Tracked when a customer visits your website.                                                                                                                                                        |
| `session_end`   | Generated 20 minutes after a customer leaves your website or closes the browser tab. Its timestamp is the [last session ping from the JavaScript SDK](https://documentation.bloomreach.com/engagement/docs/configuration#ping-options) + 30 seconds. |
| `first_session` | Derived from `session_start`. Tracked when a customer visits your website for the first time.                                                                                                       |

### Session duration

Session duration is the difference in seconds between the `session_start` and `session_end` timestamps. The `session_end` timestamp falls within 2 minutes of the customer closing the last page. The 20-minute timeout doesn't apply to duration calculations.

The 20-minute timeout means that if a customer closes the page but returns within 20 minutes, the visit counts as a single session. If they don't return, those 20 minutes aren't included in the session duration.

<Callout icon="🚧" theme="warn">
  ### Ghost sessions

  Sometimes `session_start` and `session_end` events are tracked without the customer being active. This can happen when a customer leaves your website running, their computer goes to sleep, and the browser randomly wakes up and sends a session ping without a `page_visit`. For more details and solutions, see [Ghost sessions](https://documentation.bloomreach.com/engagement/docs/ghost-sessions).
</Callout>

<Callout icon="📘" theme="info">
  ### `Special` object `timestamp` event attribute

  The `special` object `timestamp` event attribute denotes a timestamp different to the custom-tracked event `timestamp` attribute. It might be used, for instance, when you want to urgently change tracking of the timestamp to a different format (for example, string YY-DD-MM format instead of a datetime) because of a specific use case. However, it is recommended to use this solution only temporarily and aim to update the format of the custom `timestamp` event attribute to avoid confusion between the two in the long run.
</Callout>

### Using Google Analytics ID for `first_session`

If you have just started using Bloomreach and you had tracked your customers using Google Analytics before, you can use the Google Analytics ID to immediately distinguish between old and new customers also in Bloomreach. You can get the Google Analytics ID from the [Google Analytics tracker](https://developers.google.com/analytics/devguides/collection/analyticsjs/cookies-user-id#getting_the_client_id_from_the_cookie). Google Analytics ID is written in the form `1.2.286403989.1366364567` and its last part (behind the last dot) is the timestamp of the first session. You can extract it from the Google Analytics ID using an expression and store it as a customer attribute.

<Callout icon="🚧" theme="warn">
  ### Customer's location inaccuracies

  As all the attributes that localize the customers are based on their IP, they depend on the quality of the IP infrastructure. The `country` and `city` attributes are generally reliable, however, the `latitude` and `longitude` are often not (as they are a more precise measure of the customer's location).
</Callout>

### session\_start and session\_end activity properties

`activity` properties are sent by the [JavaScript SDK](https://documentation.bloomreach.com/engagement/docs/js-sdk) in session pings.

| Properties   | Description                                                                                                                       |
| :----------- | :-------------------------------------------------------------------------------------------------------------------------------- |
| activity     | It is set by the SDK when `ping.activity` is enabled in the configuration.                                                        |
| created      | It is the timestamp of the ping that originally started the session (in other words, it is the session start timestamp).          |
| last\_update | It is the time of the last `session_ping` received (so stripped of the internal logout timeout before the `session_end` appears). |

### Weblayer events in scenarios

When a weblayer runs in a scenario, the platform tracks both a `campaign` event `(action = serve)`  and a `banner` event `(action = show)`. These 2 events measure different things.

For details, see [Weblayers in scenarios](https://documentation.bloomreach.com/engagement/docs/weblayers-in-scenarios#evaluate-performance).

#### Values of the **code** attribute

`Code` attribute gives you the SMTP error or reply code received from a server after you send out a campaign email. The `status` attribute is based on these codes, however, it is useful to also know the code itself as it is more precise in assessing what happened to the email. The following [link](https://serversmtp.com/smtp-error/) contains a list of codes and their corresponding meanings. For these to work correctly, you need to have a [Mailgun integration](https://documentation.bloomreach.com/engagement/docs/mailgun-integration). Even though SMTP codes are reliable for most customers, beware that small email providers often send alternative SMTP codes that will not be recognized.

<Callout icon="📘" theme="info">
  ### Tracking clicked event

  Links to your webpage sent out in a campaign lead to our CDN domain first so that the `clicked` event is tracked. After that, the customer is redirected from the CDN domain to your webpage.
</Callout>

<Callout icon="🚧" theme="warn">
  ### Issues with the opened event

  `Opened` event tracked for Gmail does not guarantee that the recipient had indeed opened your email. Gmail's servers sometimes download external images from emails into their cache in advance. As we use these images to track whether the customers opened the email, we get a fake open event every time Gmail's servers do this. Moreover, email providers sometimes block the loading of the images we use for the tracking of the `opened` event so even if your email seems to be just `delivered` it might, in fact, be opened.
</Callout>

#### Bounce management

When an email doesn't get delivered, there might be multiple reasons why it happened. We collect the failure feedback from our email providers and automatically assign it to bounce categories, such as soft or hard bounces. ### Status name change and filters migration

In 1.173 we unified the statuses of email campaign events from email providers and renamed them to meet the industry standards and improve user experience.

In the following table you can find the naming changes:

| Previous status name | New status name |
| :------------------- | :-------------- |
| dropped              | soft\_bounced   |
| soft bounced         | soft\_bounced   |
| bounced              | hard\_bounced   |
| rejected             | preblocked      |

Along with renaming, an **automatic migration** was carried out, in order to update event filters as defined below. The new naming along with the original one was used in the migration to ensure backwards compatibility. So don't worry, you probably don't have to update your analytics and campaigns manually, but keep an eye on your business critical use cases after the change to make sure everything works as expected.

The following change was done in all filters that use the renamed statuses:

* Operators `equals` have been changed to `in` and `does not equal` to `not in` and extended with new statuses.
* Operators `in` and `not in` have been extended with new statuses.

<Callout icon="🚧" theme="warn">
  Rest of the string filters `contains`, `does not contain`, `starts with`, `ends with` and `matches regex` were not changed as they are unlikely to be used for this purpose. **Manual change** is needed in case you want to use those filters in combination with the renamed statuses.

  For any other custom usage such as jinja or webhooks a **manual change** is needed as well.
</Callout>

*Example:*<br />`equals dropped` ->`in [dropped, soft_bounced]`

`in [dropped, x, y]` -> `in [dropped, soft_bounced, x, y]`

## notification\_state

The `notification_state` event is tracked by the mobile SDK when push notification tokens are generated, updated, or refreshed. This event enables support for multiple mobile applications per project by storing token information with application-specific identifiers. The event is automatically created when users grant push notification permissions or when tokens are refreshed by the operating system.

For SDK versions released on or after September 26, 2025, push tokens are stored as events rather than customer profile attributes. This allows each customer to maintain multiple tokens—one for each mobile application and device combination. For more information, see [Multiple mobile apps per project](https://documentation.bloomreach.com/engagement/docs/multiple-mobile-apps-per-project).

Each `notification_state` event contains the following properties:

| Attribute                 | Description                                   | Example values                                              |
| ------------------------- | --------------------------------------------- | ----------------------------------------------------------- |
| `push_notification_token` | Current push notification token               | Token string                                                |
| `platform`                | Mobile platform                               | `android` or `huawei`                                       |
| `valid`                   | Token validity status                         | `true` or `false`                                           |
| `description`             | Token state description                       | `Permission granted`, `Permission denied`, or `Invalidated` |
| `application_id`          | Application identifier from SDK configuration | Custom ID or `default-application` (default)                |
| `device_id`               | Unique device identifier                      | UUID string                                                 |

<Callout icon="❗️" theme="warn">
  ### Important

  **Event expiration**: `notification_state` events expire after 90 days. Customers who haven't opened your app within this period will need to reopen the app to regenerate tokens and continue receiving push notifications.

  **Project configuration requirement**: The `notification_state` event must be allowed at the project level. If event creation is disabled in project settings or blocked by schema validation, new tokens cannot be stored and push notifications will not function.
</Callout>

### Backward compatibility

For applications using the `default-application` Application ID, the system maintains backward compatibility by checking both `notification_state` events and legacy customer profile attributes (`apple_push_notification_id`, `google_push_notification_id`, `huawei_push_notification_id`) when sending campaigns. This ensures existing subscribers continue receiving notifications after SDK upgrades.
