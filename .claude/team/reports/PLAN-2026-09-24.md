## Import / export contracts

Common rules (D-04, D-22): every Bloomreach import is `preview` then `apply`. `preview` parses, validates, resolves against the current definition and returns `{diff: DiffItem[], warnings: string[], payload_hash}`. `apply` receives the same raw JSON plus `payload_hash` plus `selected_item_ids`; the server re-runs the preview, refuses if the hash differs, and applies the selected items inside one SQLite transaction, writing ChangeLog rows (from phase 3). Nothing is persisted between preview and apply.

`DiffItem = {id, op: create|update|delete|unchanged|conflict, entity_type, entity_key (human label), changes: [{field, before, after}], default_selected, note?}`. The UI renders it as a plain table with checkboxes and an Apply button.

Shared diff primitives live in `src/domain/diff/`: `diffValue(a, b)`, `diffRecordSets(before[], after[], keyFn, fieldsFn) -> Difference[]`. The import planner turns `Difference[]` into `DiffItem[]` (proposed writes); the comparison engine turns the same `Difference[]` into `Finding[]` (kinds and severities). This is the sharing D-04 requires.

### Data mapping (`data-mapping.json`)
Parse (strict, with warnings for unknown keys): `_id`, `catalogs {main, main_columns, variant}`, `consents {std_key: client_name|null}`, `custom_events []`, `customer_properties {std_key: {property}|null}`, `standard_events {std: {event: {type, filter[]}|null, <std_field>: {property}|null}}`. Filter item: `attribute.property`, `constraint.operator`, `constraint.operands[].value`. Supported operators `equals` (one operand) and `in` (many); anything else becomes a warning and the item is skipped.

Mapping to entities, per `standard_events.<std>` with non-null `event`:
1. Event `type` -> Event by name (create as `custom`, status `draft` if missing).
2. Each filter attribute -> Property (scope event; create as `string` if missing), linked to the event with role `discriminator`; each operand value added to `allowed_values_json` if missing (with `standard_event = std` as the hint).
3. Non-empty filter -> Variant with those conditions (name generated); empty filter -> no variant.
4. StandardEventMapping `std -> event (+variant)` with `field_map_json` from the non-`event` keys: `{property: "price"}` -> Property `price` (create if missing) linked to the event; `null` stays null.
5. `customer_properties.<k> = {property}` -> Property scope `customer`, `bloomreach_customer_property = k`.
6. `consents.<k> = name` -> ConsentCategory `name` with `standard_key = k`.
7. `catalogs` and `_id`, `custom_events` -> `Project.bloomreach_mapping_meta_json` verbatim (round trip). Catalog `main`/`variant` null while Catalogs exist in the project -> warning in the diff ("empty catalog block") and later a `unmapped_catalog` finding.

Expected diff for the fixture on an empty project (qa-roundtrip scenario 2): create events `cart_update, checkout, purchase, purchase_item, view_category, view_item`; create properties `action` (allowed `add`), `purchase_status` (allowed `success`), `product_id, total_price, total_quantity, product_ids, product_list, purchase_id, voucher_code, category_level_1..3, size, price, quantity, brand, stock_level, title`; variants `cart_update[action=add]` and `purchase[purchase_status=success]`; mappings `add_to_cart -> cart_update[action=add]`, `purchase -> purchase[purchase_status=success]`, `checkout, purchase_item, view_category, view_item` with empty filter; field renames visible as `purchase_item.total_price -> price` and `purchase_item.total_quantity -> quantity`; customer properties `address, email, first_name, gender, last_name, phone`; consent `brand_consent (newsletter)`; warning "catalog block empty".

Export: for every standard event in `bloomreach.ts` order emit either `{event: {type, filter}, <field>: {property}|null ...}` or the null shape used by the fixture (`event: null` and all fields null); `filter` items are rebuilt as `{attribute: {property, type: "property"}, constraint: {operands: [{type: "constant", value}], operator, type: "string"}}`; `customer_properties`, `consents`, `catalogs`, `_id`, `custom_events` from the entities and meta. Required unit test: import fixture into an empty project, export, deep-equal the fixture ignoring key order.

### Expiration settings (`expiration-settings.json`)
Parse: `events[] {type, filter, expiration {enabled, duration {count, units}|null}}`, `other {enabled, duration}`, `success` (ignored). `units` validated against `days|weeks|months|years`.
Mapping: `type` -> Event (create as `system` if missing: `session_start, session_end, page_visit, web_exit, consent, notification_state` are Bloomreach system events); empty filter -> `Event.expiration_json`; non-empty filter -> Variant (created like in data mapping) with `Variant.expiration_json`; `other` -> `Project.default_expiration_json`.
Expected diff for the fixture: six event creates (or updates when they exist) with expiration `session_start/session_end 3 months`, `page_visit/web_exit 30 days`, `consent disabled`, `notification_state 100 days`; project default `disabled`.
Export: `events` = every Event with non-null `expiration_json` (`filter: []`) plus every Variant with non-null expiration (`filter` rebuilt), `other` = project default (or `{enabled: false, duration: null}`), `success: true`. Round-trip test as above.

### Customer events export (`customer-events-export.json`)
Parse: `customer_id, project, events[] {type, timestamp (number), properties (object)}`; `url, events_listed, note` kept in `QaRun.source_meta_json`. Values keep their JSON types exactly.
Preview (the "diff" for this format is an import preview): creates nothing yet; returns per type: count, `resolved` (event exists), `variant` resolution per observation (`cart_update[action=add]` for `action: "add"`), unknown types (fixture: `managed_endpoint, survey, campaign, support_ticket, paper_catalogue, loyalty_update`), duplicates already present in another run (same `raw_hash`), and the run header (`kind: export_paste, actor: current user`).
Apply: creates one QaRun and the selected Observations in a transaction, then runs the comparison for the project and returns `{run, inserted, findings_summary}`. Unknown types are stored as observations with `event_id = null` and produce `unexpected_event` (info) findings; a later button "create as system event" is phase 2.
Export: `GET /export/qa-runs/:id/customer-events-export.json` re-emits the run in the same shape (events sorted by timestamp desc). Round-trip test: import fixture, export run, `events` arrays deep-equal.

## Three-way comparison engine design

Location: `src/domain/comparison/` as pure functions with no DB access; `src/backend/services/comparison.service.ts` loads snapshots from the DAL, calls the engine, and upserts Findings. Unit tests feed the fixtures directly into the pure functions.

Inputs:
- `DefinitionSnapshot`: project default expiration; events with linked properties (role, required, payload_key, data_type, formats, allowed values), variants with conditions, standard event mappings, consent categories, catalogs, identity rules.
- `MappingSnapshot`: either parsed from a pasted `data-mapping.json` (preview) or built from stored StandardEventMapping, consent `standard_key`, customer property mapping and `bloomreach_mapping_meta_json`.
- `Observation[]` from all non-archived runs (or one run for a run-scoped preview), with resolved `event_id/variant_id`.

Resolution: `event_id` by exact `event_type = Event.name`; `variant_id` by evaluating the conditions of each Variant against `properties[payload_key ?? name]` with string comparison; if a discriminator value is present but matches no variant and is not in `allowed_values` -> `unknown_variant`.

### Comparison 1: definition vs mapping
| check | kind | severity |
|---|---|---|
| Event whose properties include a discriminator with `allowed_values[].standard_event` set, but no StandardEventMapping targets that standard event | `unmapped_standard_event` | warning |
| StandardEventMapping field mapped `null` while the definition links a property of the same name to the event (or a required property has no std field) | `unmapped_property` | warning |
| Field map points at a property not linked to the event, or std field name differs from `payload_key` and the definition has no rename recorded | `rename_mismatch` | warning |
| ConsentCategory without `standard_key` while the mapping has an unfilled standard consent, or mapping name differs from the category name | `rename_mismatch` | warning |
| Catalogs exist and mapping `catalogs.main` and `variant` are null | `unmapped_catalog` | warning |
| Event/variant expiration in definition differs from a pasted expiration settings file (preview only) | `expiration_mismatch` | warning |
Findings from a pasted (not applied) mapping are returned to the preview as `warnings` and are not persisted.

### Comparison 2: mapping vs observations
| check | kind | severity |
|---|---|---|
| Mapped std field whose property is absent in every observation of the mapped event/variant | `missing_required` | error |
| Observed discriminator value that no StandardEventMapping covers (e.g. `action: "remove"` when only `add` is mapped) | `unknown_variant` | warning |
| Consent observation `category` equals a standard key that the mapping renames (fixture: `newsletter` observed, mapping says `brand_consent`) | `rename_mismatch` | warning |
| Observed event type that is the `type` of a mapped standard event but the filter never matches | `unmapped_standard_event` | warning |

### Comparison 3: definition vs observations
| check | kind | severity |
|---|---|---|
| Required property absent in an observation of its event/variant | `missing_required` | error |
| JSON type of value differs from `data_type` (`"28"` vs number; `"TRUE"` vs boolean; `timestamp` accepts number or ISO string) | `type_mismatch` | error |
| Value violates a `data_format` (email, uri, iso8601, currency_code, ...) | `format_violation` | warning |
| Value not in `allowed_values` for role `normal` or `context` | `enum_violation` | error |
| Value not in `allowed_values` for role `discriminator` | `unknown_variant` | error |
| Same property name observed with different JSON types across events in the scope (`product_ids` array on purchase, string on checkout and cart_update) | `shape_inconsistent` | error |
| For mapped `purchase` and `purchase_item`: sum over items of `total_price_field * total_quantity_field` grouped by `purchase_id` differs from purchase `total_price` by more than 0.01 (fixture: 28.4 vs 28) | `rounding_drift` | warning |
| Payload key not linked to the event | `unexpected_property` | info |
| Observed type with no Event | `unexpected_event` | info |
| Event (status not `ignored`) with zero observations in scope | `missing_event` | error for `agent_session` runs, warning for `export_paste` |
| Observation older than the effective expiration window of its event still present | `expiration_mismatch` | info |

Expiration suppression: `missing_event` is not raised for an event whose effective expiration is enabled when the newest observation timestamp in the scope is older than `now - duration` (Bloomreach would have deleted it anyway) or when the scope contains no observation newer than the window at all. Effective expiration = `Variant.expiration_json ?? Event.expiration_json ?? Project.default_expiration_json`.

Required reproduction on `customer-events-export.json` (qa-roundtrip scenario 4), with the definition produced by applying `data-mapping.json` and setting `total_price` and `price` to `number`/`money`, `is_new` to `boolean`, `quantity`, `total_quantity`, `stock_level` to `number`:
- `type_mismatch` purchase.total_price `"28"` vs number
- `type_mismatch` purchase_item.is_new `"TRUE"` vs boolean (property `is_new` must exist on `purchase_item`; the test fixture definition adds it)
- `shape_inconsistent` product_ids: array on purchase, string on checkout and cart_update
- `rounding_drift` purchase 28 vs items 28.4
- `unknown_variant` when a test mutates `action` to `"remove"`
- `unexpected_event` for `managed_endpoint, survey, campaign, support_ticket, paper_catalogue, loyalty_update`

### Finding lifecycle and certification (D-05, D-21)
- `fingerprint = comparison|kind|event_id|variant_id|property_id|detail` where `detail` is the discriminating value (observed type, offending value class). `runComparison` recomputes for the whole project over all non-archived runs, upserts by fingerprint (`last_seen_at`), and marks findings not produced this time as `resolved`. No manual mute; archiving a run or fixing the definition is the way to clear a finding.
- `certified(event) = status != ignored AND count(open findings, severity error, any comparison, event_id = event) == 0 AND count(observations for event in non-archived runs) >= 1`. Computed in `document.service` and returned as `{certified, reason}`; never stored.
- Coverage grid: for an event, rows = variants (or the base event when none), columns = allowed values of each context-role property, cell = observation count matching the variant conditions and `context_values_json[property] ?? properties[payload_key]`. Unobserved cells are listed, not turned into findings.

## MCP server design (D-11, D-19)

Hosting: a sibling Node process, `src/mcp/server.ts`, started by `npm run mcp` (`tsx src/mcp/server.ts`) with `@modelcontextprotocol/sdk` stdio transport. It imports the same DAL and service modules as Express and opens the same SQLite file (WAL). Reasons: the stdio transport must own stdin and stdout of its process (the `tsx watch` API server logs to stdout); Claude Code and Claude in Chrome launch MCP servers as child processes from a command, which fits a dedicated entry point; agents can read definitions even when the web app is not running; no HTTP or auth layer is needed locally. An HTTP transport mounted on Express is a later option; the tool implementations are transport-agnostic (`src/mcp/tools/*.ts` call services, not routes).

Configuration: repo root `.mcp.json` entry `e3-tracking` with `command: npx`, `args: ["tsx", "src/mcp/server.ts"]`, env `E3_DB_PATH`, optional `E3_PROJECT_KEY` default. Every tool takes `project_key` (falls back to the env default). Outputs are JSON text content; errors are MCP tool errors with the API error code.

| tool | kind | input | output |
|---|---|---|---|
| `list_projects` | read | - | `[{key, name}]` |
| `list_events` | read | `project_key, status?` | events with variants, discriminators, contexts, required properties, certification |
| `get_event_card` | read | `project_key, event (name or id)` | `EventCard` (same as capability 14) |
| `list_use_cases` | read | `project_key` | use cases with ordered requirements |
| `get_use_case` | read | `project_key, use_case (code or id)` | use case, ordered requirements resolved to event/variant/property names, narrative |
| `get_expected_payload` | read | `project_key, event, variant?` | `{required: {key: type}, optional: {...}, discriminator_values, context_properties, example}` |
| `list_findings` | read | `project_key, event?, severity?, comparison?, status?` | findings |
| `submit_observation` | write | `project_key, qa_run_id?, event_type, properties, page_url?, context_values?, timestamp?` | observation (creates an `agent_session` run when `qa_run_id` is omitted; `actor` from `agent_name` param) |
| `submit_observations_batch` | write | `project_key, qa_run_id?, export: {customer_id, project, events[]}` | run and count (Bloomreach export shape) |
| `finish_qa_run` | write | `project_key, qa_run_id, notes?` | run |
| `run_comparison` | compute | `project_key, scope: {event?, qa_run_id?}` | findings summary and list |
| `get_coverage_grid` | compute | `project_key, event? or use_case?` | grid cells observed/unobserved |
