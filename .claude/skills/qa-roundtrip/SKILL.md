# QA round trip

Fixtures: `.claude/team/samples/customer-events-export.json`, `data-mapping.json`, `expiration-settings.json`.

## Standard scenarios
1. **App boots**: start via the `run` skill or `.claude/launch.json`; no console errors on load.
2. **Mapping import**: paste `data-mapping.json`. Expect a diff listing events, variants (`cart_update[action=add]` mapped to add_to_cart, `purchase[purchase_status=success]`), renames (purchase_item total_price to price), consents (newsletter to brand_consent), and the empty catalog block flagged. Apply. Verify entities exist.
3. **Expiration import**: paste `expiration-settings.json`. Expect per-event expiration set (session_start 3 months, page_visit 30 days, consent disabled) and the `other` default recorded.
4. **Events export import**: paste `customer-events-export.json`. Expect observations created and, on a full comparison run: 35 open findings (11 error / 4 warning / 20 info) after data mapping + expiration settings + the round-trip recipe's type edits + this export alone, or 77 or 78 open findings (40 error / 37 or 38 warning, one missing_event depends on the order of the Data Manager applies) once both Data Manager files (scenario 8) are also applied; including at least:
   - `type_mismatch`: purchase.total_price "28" string vs Number
   - `shape_inconsistent`: product_ids array on purchase, string on checkout and cart_update
   - `type_mismatch`: purchase_item.is_new "TRUE" string vs Boolean
   - `rounding_drift`: purchase_item.price 28.4 vs purchase.total_price 28 (if the rule is implemented)
   - `unknown_variant` if a discriminator value is outside the enum
5. **Export**: export mapping and expiration JSON. Diff against the fixtures; every difference must be explained by an intended change.
6. **CSV export** (phase 3, active): on the fixture project open Settings, Export; download `events.csv` and `properties.csv`; the first line equals the header list in `docs/EXPORTS.md`; the row count equals the Events and Properties table counts; open in a spreadsheet, `allowed_values_json` shows as a JSON string.
7. **Certified logic** (T-2-09 fix round, D-42): after the fixtures are applied and a comparison run, `cart_update` shows certified `yes` (observed, zero error findings). Create a property `coupon_code`, attach it to `cart_update`, mark it required (the fixture's `cart_update` observation does not carry it, so this is guaranteed to produce a `missing_required` error, unlike `total_price`, which the fixture observation already carries); run comparison: certified flips to `no` with reason `open_errors: 1`. Revert `coupon_code` to not required; run comparison: certified flips back to `yes`. Acknowledge path (D-42): with `coupon_code` required again and the finding open, resolve the finding by hand (Findings page Resolve button, or `PATCH /findings/:id {status: 'resolved'}`); certified stays `no`, now with reason `acknowledged_errors: 1` (never `open_errors`) — a manual resolve is an acknowledgement, not a fix, and must not flip certification to `yes` while the problem still reproduces. Revert `coupon_code` to not required and run comparison again: the finding's fingerprint stops reproducing, the acknowledgement marker clears automatically, and certified is `yes` again.

8. **Data Manager round trip** (phase 2, D-28): paste `data-manager-customers.json`, preview shows 101 properties in groups Personal Data, Campaign Data, Order Data plus the default group; apply; paste `data-manager-events.json`, preview shows 61 events (55 in the default group plus the 6-event MentionMe group) incl. purchase with total_price typed number from user; apply; export both and deep-equal against the fixtures with no ignored fields. Run comparison: findings with comparison id data_manager where the Data Manager holds a string from data and the definition says number: purchase_item.price and quantity, cart_update.total_price and total_quantity, checkout.total_price, view_item.price and stock_level. purchase.total_price is number and user-defined in the fixture and must not produce a finding. Note: the two Data Manager paste boxes are plain textareas with no file upload; `data-manager-events.json` (about 360 KB single-line) is impractical to paste by hand. QA may instead call `POST /api/projects/:id/import/data-manager-events/preview` (raw fixture JSON as the body) then `/apply` (`{payload, payload_hash, selected_item_ids}`) directly, and the `-customers` equivalents; same service as the UI, so the result is identical.
9. **History** (phase 3): edit `cart_update` description, the event editor History section shows one row with before/after and your user name; apply `data-mapping.json` on an empty project, the History page shows one batch with source `import:data-mapping` containing the created entities; delete a property link, the row appears under the event.
10. **Backup and restore** (phase 3): upload one trigger screenshot on `purchase`; download `backup.json`; on Clients choose Restore backup, paste the file, preview counts match the source tables, apply with key `fixture-copy`; the new project's Events, Properties, Variants, Use cases, QA runs, Findings counts equal the source; the screenshot renders on the restored `purchase` card; the source project is unchanged.
11. **Use case library** (phase 3): paste `samples/use-case-library-sample.json` on the Use case templates page; preview shows three `create` items; apply; instantiate `UC-01` into the fixture project: a use case `UC-01` with requirements resolved to `cart_update[action=add]`, `product_id`, `total_price`, `checkout`, `email`, and a generated narrative; instantiate `UC-02`: requirements resolve against the fixture's `purchase`/`purchase_item` mappings, including a `catalog_attribute` requirement (`image`, resolved against the project's main catalog fields) and a `consent` requirement (`newsletter`, resolved against consent categories); instantiate `UC-03`: the `wishlist_add` requirement has status `gap` with a note; re-paste the file, every item is `unchanged`. Extended (D-55): rename the fixture `purchase` event to `transactions`, remove the purchase mapping, instantiate `UC-02` again under a new code; the resolve preview returns the purchase targets unresolved with candidates; map `transactions` (and its variant/properties) in the dialog and apply; the requirement resolves, a new standard event mapping purchase -> transactions appears on the Standard events page and in the exported `data-mapping.json`.
