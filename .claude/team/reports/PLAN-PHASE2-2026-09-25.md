## Comparison engine design (comparisons 1, 2, 4 and the rules evaluator)

Layout: `src/domain/comparison/` keeps one pure module per comparison (`definitionVsMapping.ts`, `mappingVsObservations.ts`, `definitionVsObservations.ts`, `definitionVsDataManager.ts`) plus shared `valueChecks.ts` (extracted from comparison 3: `jsType`, `matchesDataType`, `FORMAT_CHECKS` incl. `e164_phone`, `long_text` no-op) and `snapshot.ts` (the `DefinitionSnapshot` type, extended with `class`, `pii`, `item_schema`, `rules`, `identity_rules`, `consent_categories`, `catalogs`). `src/domain/rules/` holds the evaluator. `comparison.service.ts` becomes the orchestrator: build snapshots once, build observations once (batched resolver), run the four engines and the rules evaluator, upsert by fingerprint, resolve stale fingerprints per comparison id, return `{open, produced, resolved, by_comparison}`.

Engine-wide rules (D-29, seed 6): only `class = custom` events are validated; observations resolved to sdk/platform events are skipped by comparisons 2, 3 and the rules evaluator, and never `missing_event`; unresolved types in `KNOWN_SYSTEM_EVENT_TYPES` stay suppressed. `SDK_DEFAULT_PROPERTIES` never raise `unexpected_property` and are never `unmapped_property`. Fingerprints keep the D-21 shape `comparison|kind|event|variant|property|detail`.

Batched resolution (carry-over N+1): `eventResolution.ts` gains `buildResolver(projectId)` that loads events, links and variants once and returns `resolve(eventType, properties)`; `buildEngineObservations` uses it and writes changed resolutions in one transaction. The customer-events import uses the same resolver.

### Rules evaluator (`src/domain/rules/`, D-30, D-31)
Expression representation: typed JSON parts, no string DSL. Grammar (`types.ts`):
```
Operand  = {ref: 'property', property_id}
         | {ref: 'list_field', property_id, field}            // per item of a list property
         | {ref: 'constant', value}
         | {ref: 'product', left: Operand, right: Operand}     // per item, e.g. price * quantity
         | {ref: 'aggregate', fn: RuleAggregate, of: Operand}  // over list items or child events
Arithmetic = {left: Operand, comparator: RuleComparator, right: Operand}
Membership = {needle: Operand(property), haystack: {property_id, field}}
Bound      = {subject: Operand(property), check: RuleBoundCheck, bound?: Operand(constant)}
CrossEvent = {child_event_id, join: {parent_property_id, child_property_id}, child: Operand(aggregate over child events), comparator, target: Operand(parent property)}
```
Files: `operators.ts` is the registry: `AGGREGATES: Record<RuleAggregate, (xs: number[]) => number>`, `COMPARATORS: Record<RuleComparator, (l, r, tol) => boolean>`, `BOUND_CHECKS: Record<RuleBoundCheck, (v, bound, now) => boolean>`. `evaluate.ts` walks the expression against `(observation, siblingObservations, snapshot, tolerance)` and returns `RuleOutcome {passed, expected, actual, detail}`; `validate.ts` rejects expressions whose refs are not linked to the event or whose operator is not in the registry (400 `RULE_EXPRESSION_INVALID`); `templates.ts` holds the seed templates with `applicable(eventSnapshot, mappings)` and `instantiate(...)`: `cart_update_item_in_list` (membership `product_id in product_list[].product_id`), `cart_update_totals` (sum of `product_list[].price * quantity` eq `total_price`, money; sum of `quantity` eq `total_quantity`), `purchase_items_total` (cross-event: sum over `purchase_item` of `price * quantity` joined on `purchase_id` eq `purchase.total_price`, money, `report_kind = rounding_drift`), `refund_negative_amounts` (bound `total_price lt 0` on variant `purchase[purchase_status=refunded]`, created only when that variant exists). Templates resolve property names through the standard event mapping field maps first, then by name.
Tolerance: `money` -> `max(project.money_tolerance_floor, project.money_tolerance_percent / 100 * |target|)`; `absolute`/`percent` -> `tolerance_value`; `none` -> exact. Comparators receive the tolerance.
Item schema validation runs in the same pass: for each array-typed linked property with `item_schema_json`, each item is checked for required fields, `data_type` and formats via `valueChecks.ts`; one `item_schema_violation` per `(event, property, field, reason)`.
Findings: `rule_violation` and `bound_violation` are errors, `rounding_drift` a warning; `event_id`, `variant_id`, `property_id` (the target property when it exists), `observation_id` = first failing observation; `expected_json {rule_id, rule_name, version, expression, tolerance}`, `actual_json {values}`; fingerprint detail `rule:<id>:v<version>:<join key or 'any'>`. A disabled rule produces nothing (its findings resolve on the next run).
Extension acceptance criterion: adding an operator (for example aggregate `avg` or comparator `approx`) changes only `enums.ts`, `operators.ts` and one test in `operators.test.ts`; `evaluate.ts`, the DAL, routes and UI are untouched. The task test proves it by adding `avg` in a test-only registry copy.
`computeRoundingDrift` is deleted; the engine test for scenario 4 keeps producing `rounding_drift` through the `purchase_items_total` template instantiated in the test definition, and the data-mapping import proposes that template as a `DiffItem` (`rule:purchase_items_total`, selected) whenever `purchase` and `purchase_item` mappings resolve (D-31).

### Coverage grid
`GET /events/:id/coverage` -> `{rows: [{variant_id|null, name}], columns: [{property_id, name, values[]}], cells: [{row, property_id, value, count, last_seen}], unobserved: [...]}`; rows are the event's variants plus the base row when a variant-less observation exists or no variant is defined; columns are the event's `context` role properties; a cell counts observations matching the variant conditions whose `context_values_json[property] ?? properties[payload_key]` equals the value. Unobserved cells are listed, not findings. `GET /use-cases/:id/coverage` unions the grids of the events its requirements reference. Pure function `src/domain/coverage.ts`, tests on the fixture (`cart_update[action=add]` x a test `location` context).

## MCP server (D-11, D-19, D-33)

Process: `src/mcp/server.ts`, `npm run mcp` = `tsx src/mcp/server.ts`, `@modelcontextprotocol/sdk` `McpServer` over `StdioServerTransport`, tool input schemas in `zod` (peer dependency). It calls `initDb()` and the same services as Express; all logging goes to stderr (`src/mcp/log.ts`). Repo-root `.mcp.json`: `{"mcpServers": {"e3-tracking": {"command": "npx", "args": ["tsx", "src/mcp/server.ts"], "env": {"E3_DB_PATH": "./data/e3-tracking.sqlite", "E3_PROJECT_KEY": ""}}}}`. Every tool takes optional `project_key`, defaulting to `E3_PROJECT_KEY` (D-25 Q7); a missing project is an MCP tool error with code `PROJECT_NOT_FOUND`. Handlers live in `src/mcp/tools/*.ts` as plain async functions `(input) => JSON-serialisable` so tests call them directly against `:memory:` and an HTTP transport can mount them later.

|---|---|---|---|
| `list_projects` | read | - | projects grouped by client `[{client, projects: [{key, name}]}]` |
| `list_events` | read | `project_key?, class? (default custom), status?` | `[{name, class, status, certification, variants[], discriminators[], contexts[], required_properties[]}]` |
| `get_event_card` | read | `project_key?, event` (name or id) | `EventCard` |
| `list_use_cases` | read | `project_key?` | `[{code, name, type, status, requirement_count}]` |
| `get_use_case` | read | `project_key?, use_case` (code or id) | use case with ordered requirements resolved to names and the narrative |
