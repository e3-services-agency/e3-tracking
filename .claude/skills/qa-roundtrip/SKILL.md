# QA round trip

Fixtures: `.claude/team/samples/customer-events-export.json`, `data-mapping.json`, `expiration-settings.json`, `use-case-library-sample.json` (scenario 11), `use-case-library-ucc.json` and `br-pnp/*.json` (scenario 16), `sandbox-project-backup.json` (scenario 14).

## Standard scenarios
1. **App boots**: start via the `run` skill or `.claude/launch.json`; no console errors on load.
2. **Mapping import**: paste `data-mapping.json`. Expect a diff listing events, variants (`cart_update[action=add]` mapped to add_to_cart, `purchase[purchase_status=success]`), renames (purchase_item total_price to price), consents (newsletter to brand_consent), and the empty catalog block flagged. Apply. Verify entities exist.
3. **Expiration import**: paste `expiration-settings.json`. Expect per-event expiration set (session_start 3 months, page_visit 30 days, consent disabled) and the `other` default recorded.
4. **Events export import**: paste `customer-events-export.json`. Expect observations created and, on a full comparison run: 35 open findings (11 error / 4 warning / 20 info) after data mapping + expiration settings + the round-trip recipe's type edits + this export alone, or 77 or 78 open findings (40 error / 37 or 38 warning, one missing_event depends on the order of the Data Manager applies) once both Data Manager files (scenario 8) are also applied. Reaching the 40 errors (incl. `rounding_drift`) needs a second data-mapping paste/apply after retyping `total_price` to the `money` format, so the mapping snapshot carries the money type; without it only 22 errors / 59 findings appear. Including at least:
   - `type_mismatch`: purchase.total_price "28" string vs Number
   - `shape_inconsistent`: product_ids array on purchase, string on checkout and cart_update
   - `type_mismatch`: purchase_item.is_new "TRUE" string vs Boolean
   - `rounding_drift`: purchase_item.price 28.4 vs purchase.total_price 28 (if the rule is implemented)
   - `unknown_variant` if a discriminator value is outside the enum
5. **Export**: export mapping and expiration JSON. Diff against the fixtures; every difference must be explained by an intended change.
6. **CSV export** (phase 3, active): on the fixture project open Settings, Export; download `events.csv` and `properties.csv`; the first line equals the header list in `docs/EXPORTS.md`; the row count equals the Events and Properties table counts; open in a spreadsheet, `allowed_values_json` shows as a JSON string.
7. **Certified logic** (T-2-09 fix round, D-42): after the fixtures are applied and a comparison run, `cart_update` shows certified `yes` (observed, zero error findings). Create a property `coupon_code`, attach it to `cart_update`, mark it required (the fixture's `cart_update` observation does not carry it, so this is guaranteed to produce a `missing_required` error, unlike `total_price`, which the fixture observation already carries); run comparison: certified flips to `no` with reason `open_errors: 1`. Revert `coupon_code` to not required; run comparison: certified flips back to `yes`. Acknowledge path (D-42): with `coupon_code` required again and the finding open, resolve the finding by hand (Findings page Resolve button, or `PATCH /findings/:id {status: 'resolved'}`); certified stays `no`, now with reason `acknowledged_errors: 1` (never `open_errors`) — a manual resolve is an acknowledgement, not a fix, and must not flip certification to `yes` while the problem still reproduces. Revert `coupon_code` to not required and run comparison again: the finding's fingerprint stops reproducing, the acknowledgement marker clears automatically, and certified is `yes` again.

8. **Data Manager round trip** (phase 2, D-28): paste `data-manager-customers.json`, preview shows 101 properties in groups Personal Data, Campaign Data, Order Data plus the default group; apply; paste `data-manager-events.json`, preview shows 61 events (55 in the default group plus the 6-event MentionMe group) incl. purchase with total_price typed number from user; apply; export both and deep-equal against the fixtures with no ignored fields. Run comparison: findings with comparison id data_manager where the Data Manager holds a string from data and the definition says number: purchase_item.price and quantity, cart_update.total_price and total_quantity, checkout.total_price, view_item.price and stock_level. purchase.total_price is number and user-defined in the fixture and must not produce a finding. Note: the two Data Manager paste boxes are plain textareas with no file upload; `data-manager-events.json` (about 360 KB single-line) is impractical to paste by hand. QA may instead call `POST /api/projects/:id/import/data-manager-events/preview` (raw fixture JSON as the body) then `/apply` (`{payload, payload_hash, selected_item_ids}`) directly, and the `-customers` equivalents; same service as the UI, so the result is identical.
9. **History** (phase 3): edit `cart_update` description, the event editor History section shows one row with before/after and your user name; apply `data-mapping.json` on an empty project, the History page shows one batch with source `import:data-mapping` containing the created entities; delete a property link, the row appears under the event.
10. **Backup and restore** (phase 3): upload one trigger screenshot on `purchase`; download `backup.json`; on Clients choose Restore backup, paste the file, preview counts match the source tables, apply with key `fixture-copy`; the new project's Events, Properties, Variants, Use cases, QA runs, Findings counts equal the source; the screenshot renders on the restored `purchase` card; the source project is unchanged.
11. **Use case library** (phase 3): paste `samples/use-case-library-sample.json` on the Use case templates page; preview shows three `create` items; apply; instantiate `UC-01` into the fixture project: a use case `UC-01` with requirements resolved to `cart_update[action=add]`, `product_id`, `total_price`, `checkout`, `email`, and a generated narrative; instantiate `UC-02`: requirements resolve against the fixture's `purchase`/`purchase_item` mappings, including a `catalog_attribute` requirement (`image`, resolved against the project's main catalog fields) and a `consent` requirement (`newsletter`, resolved against consent categories); instantiate `UC-03`: the `wishlist_add` requirement has status `gap` with a note; re-paste the file, every item is `unchanged`. Extended (D-55): rename the fixture `purchase` event to `transactions`, remove the purchase mapping, instantiate `UC-02` again under a new code; the resolve preview returns the purchase targets unresolved with candidates; map `transactions` (and its variant/properties) in the dialog and apply (the mapping-step API needs an explicit `variant_id` next to `event_id`, otherwise the variant and variant_property requirements silently stay `gap`); the requirement resolves, a new standard event mapping purchase -> transactions appears on the Standard events page and in the exported `data-mapping.json`.
12. **Shared view** (phase 4, D-48/D-50): on the fixture project, set a marker on an internal-only field (`agent_instructions` on `purchase`, or a use case's `internal_notes`), upload one trigger screenshot on `purchase`, then Settings -> Generate a share link with access `read`. Open it in a private/incognito window: no login; project header with client name; custom events first, sdk/platform collapsed in `<details>`; the `purchase` trigger screenshot loads through `/api/shared/<token>/files/...`; use cases show narrative and `documentation_url`; both "Download JSON" and "Download HTML" return 200; no edit controls anywhere and no comment form (read access). Grep both downloads and the DOM for the marker from step 1 -- zero occurrences. Revoke the link (Settings); reload the same URL -- "This link is not valid." (404 `SHARE_NOT_FOUND`). A malformed token (`/tracking-plan/shared/%ZZ`) is a known dev-server-only issue (Vite's own static middleware decodes before the app runs, any path); not a scenario failure on the current localhost setup, re-verify on the real host at phase 5.
13. **Shared comments** (phase 4, D-49 amendment: one shared thread): set access to `comment`. In the private window, post a comment on an event card, a use case, or a requirement row with author "Client QA" -- it appears immediately in the shared view; internally, the Comments page and that entity's comments panel show it with a `via share` badge. Post an internal reply on the same anchor from inside the app: it is visible back through the share link too (comments are one shared thread, not two separate ones -- an internal reply is client-visible by design unless flagged Internal only). Post an internal comment with "Internal only" checked: it is absent from the shared page and from the public `GET /api/shared/<token>/comments`. Set Settings, "Show internal comments on the shared view", to "Only comments posted through the link": a plain internal reply disappears from the shared page while the client's comment stays (set it back to "All comments" afterwards). Resolve the comment internally (Comments page or the panel's resolve toggle) -- the resolved state and `resolved_by` never appear on the shared side. Switch access back to `read`: the comment form disappears from the shared view, and a direct `POST /api/shared/<token>/comments` returns 403 `SHARE_READ_ONLY`. A body key outside `entity_type`/`entity_id`/`author_name`/`body` (e.g. `resolved`) is 400 `FIELD_NOT_ALLOWED`. Backup now includes the comment; a restore carries it (still one thread, same `via_share` value).
14. **Getting started and sandbox** (phase 4, D-60, T-4-09): Clients page, "Create a sandbox" -- restores the bundled backup as a new project, key `sandbox-acme-eu` (a second sandbox created the same way gets `sandbox-acme-eu-2`, never a doubled `sandbox-sandbox-...` key), "SANDBOX" badge in the switcher with no reload needed. Selecting it (lean sandbox since T-4-11A, "Acme EU (sandbox)"): 15 events (session_start, session_end, page_visit, view_item, view_category, search, cart_update, checkout, purchase, purchase_item, consent, campaign, banner, wishlist_update, newsletter_signup), 50 properties (9 customer incl. the 7 system ones with format hints, 41 event), 53 definitions (`action` has 3 named), 5 variants, 1 bundle, 9 standard mappings, 4 rules, 4 catalogs (products_gb main and live, variants_gb variant role, products_cz, variants_cz; 7 fields each with an item_id lookup key plus a regular product_id/variant_id field; one deliberate CZ stock_level type drift), 2 sources (Shopify storefront via GTM data layer as the project default; Order system via Tracking API on purchase, purchase_item, consent), 5 consent categories, 3 identity rules, 3 use cases (`UC-01` live, `UC-02` in_progress transactional, `UC-03` proposed; 17 requirements, 1 gap `wishlist_add`), 1 QA run with 16 observations, 4 comments, 2 trigger screenshots; 15 open findings (rename_mismatch 4, state_list_mismatch 2, unknown_variant 2, shape_inconsistent 1, type_mismatch 1, unmapped_catalog 1, missing_event 1 for `checkout`, rounding_drift 1, format_violation 1, catalog_schema_drift 1 from the `catalogs` comparison) plus exactly 1 resolved with `resolved_by: 'user'` (enum_violation). Restore under 1 s, backup about 390 KB. Getting started on the sandbox: exactly 9 steps, 4 done (open: the three imports, "Review property types", "Create a share link"); "Go" on the share step navigates to Settings, which shows a sandbox-specific sentence and asks for confirmation before generating (D-60: a sandbox refuses a share link without an explicit force). On a brand-new empty project, Getting started shows the same 9 steps with "Create a client and a project" and "Review property types" already done (vacuously -- a project exists, and zero properties means zero open type-mismatch findings); every list page (Events, Properties, Catalogs, Identity rules, Consent categories, Use cases, Use case templates, QA runs, Findings) shows a one-sentence empty state with an action button (Use case templates is non-empty since its library is global). Bulk-delete a non-active sandbox from the Clients page -- succeeds; deleting the *active* sandbox moves the shell to a surviving project (or clears it), never a 404 loop. Help page (sidebar): 7 tabs (the 6 docs plus Glossary), markdown rendered as real headings/lists (no raw `#`/`**` in the rendered text), 11 glossary terms present; a glossary tooltip appears on at least one page header or table column (e.g. Events page "Certified" column, History page "Batch" filter).
15. **Property definitions** (phase 4, D-58, T-4-00): on the fixture project every property starts with one `general` definition. Use two custom-class events sharing a property (e.g. `cart_update` and `loyalty_update`; a platform-class event such as `consent` is excluded from definition-vs-observation findings by D-29/D-36, so it cannot demonstrate the enum check). Create a second definition (e.g. "loyalty action", allowed values `earn`/`redeem`) on `loyalty_update`'s `action` link via the property/event editor's definition picker; the Properties page now lists both definitions with their using events. `cart_update`'s and `loyalty_update`'s event cards carry different `allowed_values`/`data_formats` for the same `action` property. Posting an out-of-enum value against one event's link produces a finding only for that event's own definition (a discriminator role sends the value through D-03's variant-resolution path instead of a plain enum check -- still per-event-definition behaviour, not a defect). Edit `general`'s description: it mirrors onto the property row, and both a `property` and a `property_definition` row appear in History. Attempt to rename `general` -- 400; delete `general` -- 409; delete a definition still linked to an event -- 409 with the linked count; delete an unlinked definition -- 204. Data Manager events export: an event whose link uses a non-general definition carries that definition's own description in the exported attribute; other events carry their own. CSV `property_definitions` and `event_properties.definition_name` columns match `docs/EXPORTS.md`. Full JSON backup and restore: `property_definitions` rows restore cleanly into the new project (dashed UUIDs, remapped like every other id) with matching counts.
16. **pnp template import** (phase 4, D-59, T-4-08): on the Use case templates page, paste one Use Case Center `pnp_usecase` export (e.g. `.claude/team/samples/br-pnp/lwef-welcome-flow.json`) -- the page detects the format and converts it before the usual preview; preview shows one `create` item with zero warnings, the converted tags/prerequisites/expected assets visible on the detail view (documentation link, callout quote, prerequisite bullets, expected-assets list, tags/tier/flags). Apply, then instantiate on the fixture project: the use case is created with its `documentation_url` copied from the template and any target the fixture cannot resolve becomes a `gap` requirement (not a thrown error). Re-preview the same raw file: `unchanged`. Set `internal_notes`/`internal_url` on the resulting use case and the template, then re-preview the same raw file again: still `unchanged` (D-59 amendment 3 -- user-owned fields are never proposed as an update) and the internal values survive untouched; grep the tracking document JSON and the HTML export for those values -- zero occurrences. A malformed pnp document (e.g. `requirements` not an array, or a `null` requirement item) returns 200 with a warning, never a 500 or a blank page.
