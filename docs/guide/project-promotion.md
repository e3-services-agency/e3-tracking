# Promote a project snapshot into an existing empty project

This operator operation transfers a reviewed, exact project backup into an **existing empty destination** with the same project key. It preserves the destination ID, client, name, key, access grants and share/security policy. It does not create a replacement project or merge into existing content.

Enable `PROJECT_PROMOTION_ENABLED=true` only on the intended installation after a full database/files/configuration snapshot and restore rehearsal. Migration 0049 retains an immutable operational receipt. The API requires authenticated staff plus the exact application Origin; actor names supplied by the client are ignored.

1. Export the complete source backup and retain its exact UTF-8 bytes and SHA-256. Verify the source project ID separately. Refresh the source before promotion and compare all content, allowing only a naturally changed export timestamp.
2. `POST /api/projects/:destinationId/promotion/preview` with `{input}`. Input contains `source_project_id`, `destination_project_id`, `source_sha256` and the exact backup bytes as the `source_backup` string. Preview changes nothing and returns source/target hashes, the destination baseline, row counts, dependency ID map and `plan_hash`.
3. Review the complete diff. `POST .../apply` with the identical input, `plan_hash`, `destination_baseline_hash` and `human_confirmed: true`. Any changed source bytes, destination baseline, unsupported section/column, foreign dependency, collision or nonempty content blocks the operation. All inserts, explicit specification settings, one promotion audit and the receipt commit together or roll back together.
4. Verify every table and lineage, the original destination identity/security, native decision state and source-review status, mapped configuration, zero added observations and unchanged QA meaning. A replay of the exact receipt returns the same operation only while the destination fingerprint is unchanged. Later edits or validation reports make an old replay stale.

The narrow first version rejects files, embedded global templates, imported share members and any backup/export warning. It permits a pristine sequence counter and project-creation audit in the destination. Source entity IDs remain unchanged; only scoped relational `project_id` fields map to the destination. Explicit business configuration fields such as the source binding, naming and data-manager definitions transfer, while destination identity and security fields are retained.

Original decision payloads, approval details, content hashes, cited source captures and asset-link review packages remain unchanged. A receipt binds each imported decision/use-case pair to its source project ID for baseline checks. This preserves existing stale/fresh semantics without rewriting a historical approval. New amendments and follow-ups use normal destination baselines. A later changed complete source capture still creates an unapproved follow-up and blocks planning from the old basis. No promotion action approves documentation, authorizes execution, changes lifecycle, runs comparisons or certifies delivery.

The receipt retains the original source backup privately in the operational database; public responses never return it. Portable project backups exclude operational promotion receipts. An ordinary portable restore remains a separate operation that creates a new project and makes restored decision/asset authority historical and read-only. A full database restore requires the established operational recovery process, including connector revocation protections.
