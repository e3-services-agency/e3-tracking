# Decision inbox

This is a native, project-scoped E3 Tracking view at `/tracking-plan/p/<key>/decisions`.
Enable the API only on the intended installation with `DECISION_INBOX_ENABLED=true`.
The pilot uses SQLite migration `0046_decision_inbox.sql`. It adds no external service or model dependency.

## Protocol

1. A proposal contains a stable key, revision, evidence links/hashes/capture times, confidence rationale, audiences, recommended reviewer and exact documentation patches. It may also include typed `native_changes`: use-case status transitions, event variant creates and explicit required/optional flags on existing event-property links, and shared property type/item-schema updates with an explicit optional payload derivation diff.
2. `POST /api/projects/:id/decision-inbox/preview` with `{proposal}` validates native requirement targets without retaining writes and returns a content hash. `/import` requires the same proposal and hash; identical replay returns the existing revision. Import records AI authorship and no approval.
3. The human reviews the exact changes. For a native proposal, the confirmation checkbox plus **Approve and apply** immediately performs the listed status transitions, variant creates, required-field flags and shared property schema/derivation updates, documentation patches and execution receipt in one transaction. The card shows the resulting entity names/IDs and status values. No agent or background worker is involved. Documentation-only proposals retain **Approve documentation**, which appends notes and adds requirements with status `open`. Neither action certifies QA, removes requirements or calls Bloomreach.
4. **Amend** creates a new unapproved revision and retains the superseded record. Native amendments can edit expected/new status, expected/new required flags, condition operators and literal values, or remove a proposed change. A reason is required. **Defer** leaves documents unchanged and permits later review. **Reject** closes the proposal without changing documents.
5. **Request execution plan** records remaining planning work and grants no external write permission. It is not needed to apply native changes included in **Approve and apply**. External implementation and observed verification remain separate.

Actions use `POST /api/projects/:id/decision-inbox/:decision/actions` with `content_hash`, `action`, `human_confirmed: true`, `note`, and (for amendment) a full `amendment` proposal. The server uses its authenticated actor; supplied actor names are ignored. These routes are absent from shared/public views. In local mode the recorded local identity is unverified; neither roles nor local approval establish client commercial authority.

## Review queues

The default **E3 changes** queue shows current unapproved proposals with explicit executable changes. **Business choices** holds unresolved documentation/policy questions, including those requiring more input or implementation support; its approval records the stated documentation and does not imply native execution. **Completed / closed** and **All revisions** retain approvals, receipts, rejections and earlier wording. Nothing is auto-approved or deleted by moving between views.

A business proposal can include explicit `questions` with stable IDs, labels and nullable answers. **Input required** blocks approval while an answer is missing. The card shows **What you need to decide** immediately; open **Amend** to enter answers and save a new unapproved revision. Approval separately records the reviewed answers in use-case notes. It does not execute external work or resolve missing inputs on the reviewer's behalf.
Cards begin as compact summaries showing actual approval writes and reconciliation status. Ready proposals remain usable after unrelated edits. Partially satisfied proposals stay pending when any proposed operation, note or requirement remains. Already satisfied and superseded proposals move out of pending without creating approval authority. Expand one card to inspect evidence, exact operations, amendments and the receipt. Search by key, summary, target or text; direct decision/record links reveal the relevant revision even outside the current filters. A zero action count means no executable proposal is awaiting approval, not that all tracking work is done. Documentation-only cards explicitly count notes and requirement rows; their stated benefit is a recommendation, not a claim that saving notes fixes configuration.

**Retry** reloads decisions after a connection failure and retains previously loaded records. If an action was saved but refresh failed, inspect the returned record after reload. If the write response was lost, the outcome is unknown until readback; further actions remain locked to prevent accidental duplicate decisions. Backend replay protection remains authoritative.

## Information and confidence

Every role sees the same decision IDs and revisions. The role filter selects relevant work for PM, technical consultant, business consultant and customer success. It is a presentation filter, not access control or a separate knowledge copy.

High/medium/low means evidence confidence with an explicit rationale. It does not measure implementation success or probability of a business outcome. Captured activation, historical sign-off and QA verification remain distinct facts.

## Integrity and recovery

Every read and refresh reconciles the immutable proposal against current E3 state. Returning to the browser tab also refreshes this view. A version-2 proposal stores the exact fields relevant to its writes: a status transition does not depend on unrelated use-case owner, description or lifecycle notes, and a required flag does not depend on unrelated event prose. Notes and new requirements retain their own dependencies. Variant discriminator validation, schema targets and cited-source checks still apply. No GET changes configuration, revisions, history or approval authority.

Relevant conflicts show **Reviewed before**, **Current**, **Intended** and a specific next step. An earlier hash-only proposal cannot disclose a field value it never retained: **Review current data to prepare this proposal** states that limitation. **Review updated proposal** previews a refreshed version against current relevant data. **Save unapproved revision** retains the earlier record and creates a fresh proposed revision; it changes no configuration and infers no approval. The reviewer then separately reviews and explicitly approves its exact writes. Source-review and restored records retain their stricter boundaries.

The bounded refresh endpoints are `POST /api/projects/:id/decision-inbox/:decision/reconcile/preview` with the old `content_hash`, then `/reconcile/apply` with that old hash and returned `preview_hash`. A changed preview is rejected rather than silently rebased. Ordinary approval also recomputes relevant dependencies inside its transaction. Already satisfied native operations are not executed again; incomplete documentation/requirement work remains reviewable. Native variant validation rejects overlapping positive predicates because E3 resolves the first matching variant.

Native approval uses action `approve_and_apply`; `approve_documentation` refuses proposals containing native operations. The supported operations are `{op:'use_case_status',use_case_id,from,to}` (including explicit null for an unset status) and `{op:'create_variant',event_id,conditions,description?}`. Required-field operations use  `{op:'event_property_required',event_id,property_id,from,to}` with strict boolean values. They update only an existing link, never create a link or change a shared property definition. Both Required to Optional and Optional to Required are explicit transitions; unchanged, duplicate, missing, deleted or stale targets are refused. Receipts contain the composite event/property identity and exact before/after booleans. The `property_schema` operation changes one shared property's explicit `data_type`, `item_schema_json` and, only when included in both snapshots, `derivation_json`. Its before/after values and all affected linked events are disclosed. This can affect validation and newly generated payload examples for every linked event. It does not install producer code, GTM tags or Bloomreach configuration. Existing shared definitions, identifiers, QA observations and reports outside the explicit operation remain unchanged. Every proposal retains its associated use-case documentation patch. Unsupported operations and arbitrary object patches are rejected. Preview validation rolls back all temporary writes. Failure rolls back every operation and the approval. Repeating an approved action returns its existing receipt and never re-executes it. Equivalent existing variants are recorded as already present; they are not silently rewritten.

Existing documentation approvals do not acquire native execution authority. Automatically generated source-review follow-ups strip native operations and their baselines; concrete native changes need their own reviewed revision. Applied native changes remain stored with the existing documented state and an explicit `approve_and_apply` execution receipt, displayed as **E3 changes applied · QA pending**. No schema migration is required.

Backup exports include decision revisions/events. Restore into a new project preserves original payload hashes and history but marks the records read-only: authority is not transferred. They must be re-proposed in the destination project. Back up the entire database/volume before a schema upgrade; image rollback alone is not a complete data rollback.

## Boundaries and remaining integration

Sources are captured citations. The local source-review extension below can bind selected cited content and invalidate its planning basis when a new complete capture is supplied. It does not poll remote tools. Scheduled collection, a durable runtime publisher, notifications and execution approval/verification workers remain separate work. Treat the source timestamps as the freshness boundary. Company-library promotion is also separate, requires anonymisation/review and is not performed by this inbox.

Raw client sources remain in private storage, outside committed source. Automated tests use synthetic projects; browser mutation checks must use a disposable synthetic project and cannot approve real client decisions on the user's behalf.

## Selected cited-source checks

Migration `0047_decision_source_captures.sql` retains scoped, immutable capture history. This is a manual/operator intake path for exact cited content, with no remote poller or new publisher credential.

- `POST /api/projects/:id/decision-inbox/:decision/sources/preview` accepts `{capture}` and returns the exact preview hash and before/after changes. A capture has a canonical `source_key`, `baseline_package_hash`, `package_hash`, `captured_at`, `complete`, and records containing the original citation URL, author, occurrence time and exact text.
- `/sources/apply` requires the same capture and preview `content_hash`. First binding requires the original cited package hash and complete coverage of that package's cited URLs. The operator verifies the retained package and selected records before submission; the API does not independently fetch or authenticate a remote source.
- Later complete captures compare only selected cited content. Changes elsewhere in the package do not invalidate the decision. Partial captures are retained as audit evidence without replacing complete evidence or creating false absence/invalidation. A reused package hash with conflicting cited content is refused.
- A relevant change retains the original approval and approved notes, flags the old planning basis, and atomically creates one unapproved follow-up with exact before/after text. Identical replay creates neither another draft nor another event. Reversions remain reviewable transitions; they do not silently restore authority.
- Follow-ups inherit their cited-content baseline. Later changes to the same selected source records also invalidate those follow-ups, within the same project. The source flag is sticky until a fresh reviewed basis is established; a prior approval is never rewritten.
- Wording amendments inherit existing source dependencies and any review flag. They do not count as a fresh source observation. Changing tracked citation URL/hash references through an amendment is refused; prepare a separately sourced follow-up.
- The UI links directly to the source re-review and disables stale planning. The server refuses a stale planning request even if an earlier planning intent was already recorded. No external execution worker is attached to planning requests; explicitly reviewed native E3 changes use the direct approval action described above.
- Portable backup/restore preserves source payloads/hashes and remaps relational IDs. Restored decision history remains read-only and cannot establish a new source baseline or transfer authority.

Controlled source changes belong in a disposable synthetic project. They must never be imported as real client updates. Collect actual source orders, emitted payloads and rendered results separately when verifying a correction.
All mutation POSTs require authenticated staff and the exact application Origin. A missing or cross-site Origin is rejected. Scoped promotion into an existing empty hosted project is a separate explicit operation; see the project promotion guide. It preserves original decision hashes and recorded approval/planning semantics without granting new approval or execution authority.
