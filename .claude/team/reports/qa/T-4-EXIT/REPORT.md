## Docs mismatches (not application defects, filed here per the task instruction to report wording that no longer matches the app)

- Note A: qa-roundtrip skill scenario 4 lists "78 open findings (40 error / 37 or 38 warning)" as one branch reachable by applying mapping+expiration+Data Manager+events-export, but does not mention that the rounding_drift finding (and the 40-error count) additionally requires re-pasting data-mapping.json a second time after the round-trip recipe step 4 type edits (docs/QA-LOCAL.md). The purchase_items_total rule is only proposed by the import planner at paste time when total_price already carries the money data format; retyping it after the first mapping apply does not retroactively create the rule. Without the second apply, only 59 findings appear (22 error / 37 warning, no rounding_drift). Suggest a one-line addition to docs/QA-LOCAL.md round-trip recipe: re-run the data-mapping paste/apply once after step 4 to pick up the rounding-drift rule.
- Note B: the qa-roundtrip skill scenario 11 D-55 extension says to map transactions (and its variant/property) in the dialog and apply, but does not spell out that the mapping-step API/dialog answer must carry the candidate own variant_id, not just event_id. Supplying only event_id (the first attempt) silently leaves the variant/variant_property requirements as gap even though a matching variant exists on the target event, because applyTemplateMappings (use-case-template.dal.ts) only sets variant_id when the caller passes one. Not a bug (the UI dialog presumably always supplies both), but worth a one-line clarification since the API path (used for QA per docs/QA-LOCAL.md own guidance on scripting large fixtures) needs it spelled out.
- Note C: qa-roundtrip skill scenario 15 uses the fixture consent event (class platform) as the second event in its per-event-definition enum-violation demonstration. Per D-29/D-36 (src/domain/comparison/definitionVsObservations.ts), only class custom events ever produce definitionVsObservations findings; posting an out-of-enum value on consent never fires any finding regardless of which definition its link uses, so the scenario as literally written cannot demonstrate the behaviour it describes. The actual capability (per-event-definition enum scoping) was verified instead on two custom-class events (cart_update discriminator action vs loyalty_update normal-role action) and works correctly. Suggest the scenario reference a second custom-class event carrying action (e.g. loyalty_update or back_in_stock_list) instead of consent.
